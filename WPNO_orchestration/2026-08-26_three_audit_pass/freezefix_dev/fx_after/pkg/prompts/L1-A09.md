## OBJECTIVE

For every pattern in the productive rule set, test the boundary behaviour on both sides of the match against the full delimiter inventory, and record false positives and false negatives separately.

## WHY THIS MATTERS

This exact defect is recorded in the project's own CLAUDE.md § 10 as the first of nine error classes: the pattern *bea* matched Projektbeauftragung, Beanstandung and Bearbeitung — twelve hits, none real. German compounding makes this failure mode structural rather than occasional. A pattern that is correct for English is frequently wrong for German.

## THREAT MODEL

Two symmetric failures. Over-matching: a short token embedded inside a longer legitimate compound word, producing noise until the tool is ignored. Under-matching: a boundary assumption that fails on a legitimate delimiter, so a real hit is silently missed.

## STATIC ANALYSIS

No module under `PROJECT_ROOT` may be imported. A top-level import executes code. Parse; do not import.

1. Enumerate the complete pattern set from the productive guard by AST parse. 'Every relevant article' is not a defined set on this machine, so this enumeration IS the definition, and it is recorded as evidence.
2. For each pattern record: the literal, the boundary construct used (\\b, lookaround, explicit character class, or none), the regex flags, and whether Unicode matching is enabled.
3. Classify each pattern by risk: patterns with no boundary construct, and short patterns (under five characters), are the high-risk set.
4. Record whether the guard normalises before matching, since normalisation changes what a boundary is.

## RUNTIME TEST MATRIX

Every runtime operation below is gated and requires the human approval token. Nothing here runs before that token arrives.

1. Build the delimiter inventory: start of string, end of string, ASCII space, non-breaking space (U+00A0), narrow no-break space (U+202F), newline LF, newline CRLF, comma, period, colon, semicolon, opening and closing parenthesis, double quote, German quotation marks, apostrophe, typographic apostrophe, hyphen-minus, en dash, em dash, soft hyphen, digit, uppercase letter, lowercase letter, non-ASCII Unicode letter (umlaut, sharp s), and direct concatenation with no delimiter.
2. For each pattern, generate the cross product: pattern preceded by each delimiter, followed by each delimiter, and both.
3. Add the German compound set explicitly: the pattern embedded in a longer legitimate compound, as prefix, as infix, and as suffix. Use real German compounds; construct them, do not take them from client documents.
4. Add case variants: all upper, all lower, title case, mixed.
5. Run the full matrix against the productive guard.
6. Record two separate tables. Table FP: cases that matched and should not have. Table FN: cases that did not match and should have. Never combine them into a single accuracy number.

## POSITIVE CONTROL

Each pattern must match its own literal surrounded by plain spaces. A pattern that does not match its own literal is broken independently of boundaries.

## NEGATIVE CONTROL

Each pattern must not match a string that shares no substring with it. This proves the harness is not reporting matches indiscriminately.

## MUTATION CONTROL

For a pattern that uses \\b, replace the boundary construct in a sandbox copy with nothing and re-run the compound cases. The false-positive count must rise. This proves the boundary construct is what is being measured.
