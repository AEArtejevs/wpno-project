## RISK

## OBJECTIVE

Prove that the productive output guard rejects the known-bad report, and that the rejection is caused by the rule intended to catch it rather than by an unrelated failure.

## WHY THIS MATTERS

A guard that rejects for the wrong reason is a guard that will accept the next bad input that avoids the accidental trigger. 'It failed, so we are protected' is the weakest possible evidence, and it is the evidence usually offered.

## THREAT MODEL

## STATIC ANALYSIS

No module under `PROJECT_ROOT` may be imported. A top-level import executes code. Parse; do not import.

1. FIRST: resolve identity. The audit specification names 'report_bad'. This identifier does not exist in PROJECT_ROOT. Establish what the known-bad input is on this machine, from evidence, and record the mapping. If it cannot be established: BLOCKED_TARGET_IDENTITY_UNCERTAIN.
2. SECOND: resolve which guard version is productive. Three exist; two are named VERALTET and carry a .py.txt extension. A filename marker is documentation, not evidence. Apply the same execution-path rule as L1-A03.
3. PYTHON_AST_PARSE the guard. Enumerate every rule, every pattern, every threshold, and the exact condition that produces a rejection.
4. Map each rule to an identifier so a rejection can be attributed to one rule.
5. Determine the guard's output contract: exit code, printed verdict, structured result. Record whether exit code and semantic verdict can disagree.

## RUNTIME TEST MATRIX

Every runtime operation below is gated and requires the human approval token. Nothing here runs before that token arrives.

1. Run the productive guard against the known-bad input via PYTHON_SCRIPT_RUN_SANDBOX. Record argv, exit code, complete stdout and stderr.
2. Record both the exit code and the semantic verdict, separately. A guard that prints REJECT and exits 0 is a finding.
3. Attribute the rejection to a specific rule. If the output does not identify the rule, determine it by selectively neutralising rules in a sandbox copy of the guard and observing which change makes the rejection disappear. The sandbox copy is written under the audit work directory; the original is never touched.
4. Repeat with the known-bad input trivially reformatted (whitespace, line endings) to confirm the rejection is content-driven, not layout-driven.

## POSITIVE CONTROL

A minimal input constructed to violate exactly one enumerated rule must be rejected, and the rejection must be attributable to that rule. This proves the guard is switched on and the attribution method works.

## NEGATIVE CONTROL

A minimal clean input must be accepted. If everything is rejected, rejection of the bad input carries no information.

## MUTATION CONTROL

Neutralise, in the sandbox copy only, the rule that the known-bad input is supposed to trigger. The known-bad input must then be accepted. If it is still rejected, the rejection came from somewhere else and the original attribution was wrong.

## INDEPENDENT ORACLE

The enumerated rule set from the AST parse, plus inputs constructed by this audit to isolate one rule each. The guard's own report files in authoring/ are prior artefacts, not oracles.

Forbidden as an oracle for this audit: the implementation under test, any other copy of it, any project artefact derived from it, any prior report under `docs/`, this package's own reconciliation notes, any output of the failed predecessor package, and model knowledge unsupported by a retrieved source.

## EDGE CASES

- known-bad content split across lines
- known-bad content with Unicode look-alike characters
- known-bad content inside a comment or metadata field
- input that triggers two rules at once
- empty input
- input larger than the guard's output limit

## PASS CRITERIA

The productive guard is identified with execution-path evidence; the known-bad input is identified with evidence; it is rejected; the rejection is attributed to the intended rule; exit code and semantic verdict agree; positive, negative and mutation controls all behave as required.

In addition, and without exception: positive control passed, negative control passed, mutation control passed where applicable, independent oracle used, target hash unchanged across the run, and no unresolved evidence capable of changing the conclusion. If such evidence exists the verdict is `UNVERIFIED`, not `PASS`.

## PASS_WITH_WARNINGS CRITERIA

Rejection occurs and is attributed correctly, but exit code and semantic verdict disagree, or the guard's output does not name the rule.

Every warning is named with its own evidence. A warning is not a place to put doubt about the main conclusion — that belongs in `UNVERIFIED`.

## FAIL CRITERIA

The known-bad input is accepted; or it is rejected for a reason other than the intended rule; or the mutation control shows the rejection is unrelated to the rule under test.

## BLOCKED CRITERIA

BLOCKED_TARGET_IDENTITY_UNCERTAIN — either the known-bad input or the productive guard version cannot be established from evidence.

A blocked audit is a legitimate and complete outcome. State precisely what is missing and what would unblock it. Never soften BLOCKED into PASS or into a partial pass.

## UNVERIFIED CRITERIA

Rejection observed but attribution to a rule could not be completed.
