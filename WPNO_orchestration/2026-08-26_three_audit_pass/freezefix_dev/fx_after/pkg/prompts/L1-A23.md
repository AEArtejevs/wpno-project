## OBJECTIVE

Compare every checkable rule and factual claim in CLAUDE.md against the actual state of this machine, and record each as confirmed, contradicted or uncheckable.

## WHY THIS MATTERS

An instruction file that describes a machine that no longer exists is worse than none: it directs work confidently in the wrong direction, and its confidence is what makes it dangerous. Documentation is not evidence of reality, and the only way to know which claims still hold is to check them one at a time.

## TARGET IDENTIFICATION RULE

Re-derive the target set yourself; do not adopt the binding's list as the enumeration. Then compare your enumeration against the binding. A file present in one and not the other is a finding before anything else proceeds.

Hash every candidate with `SHA256_FILE` and compare against the binding. Any mismatch means the tree changed since the package was built: stop and return `BUILD_CONTAMINATED_SOURCE_CHANGED`.

Production identity requires execution-path evidence — an import, an invocation in a script, a container command, a workflow node, a scheduler entry. Filename, version suffix, modification time, file size, documentation, comments and proximity to another file are **excluded by rule**. If production identity cannot be proven, say so; do not nominate a most-likely candidate.

## PRODUCTION PATH REQUIREMENT

State, as a separate recorded item, whether the target is on the production execution path, and on what evidence.

This machine has no runtime supervisor for most audited components: the only two WPNO LaunchAgents are an MCP health poller and a wiki ingest watcher whose watch path is outside `PROJECT_ROOT`, and the only container mounting WPNO source mounts four named files under `docker/litellm`. Everything else in scope is invoked by hand from a shell. Consequently 'productive' is frequently unprovable here, and `BLOCKED_TARGET_IDENTITY_UNCERTAIN` or `UNVERIFIED` is the correct answer rather than a qualified guess.

If the audit proceeds against a candidate rather than a proven productive copy, every conclusion must carry that qualification in its own text — not only in a footnote.

## STATIC ANALYSIS

No module under `PROJECT_ROOT` may be imported. A top-level import executes code. Parse; do not import.

1. Enumerate every checkable claim in the file, with its section and line range. A claim is checkable if it asserts something about a path, a tool, a version, a service, a repository, a permission, a configuration or an execution path.
2. Number the claims. The comparison must be exhaustive over that list; a claim skipped is recorded as skipped, not omitted.
3. For each claim record what evidence would confirm it and what would contradict it, before looking.

## RUNTIME TEST MATRIX

Every runtime operation below is gated and requires the human approval token. Nothing here runs before that token arrives.

1. For each claim, gather the evidence read-only: STAT_FILE and LIST_DIRECTORY for paths; FILE_TYPE for file kinds; GIT_STATUS_READONLY, GIT_REV_PARSE and GIT_LOG_READONLY for repository claims; PARSE_JSON_READONLY for configuration; READ_FILE_RANGE for compose files, Dockerfiles, MCP configuration, n8n workflows and LaunchAgent plists.
2. Tool and version claims: record how the version was obtained. If obtaining it requires running the tool, that is a gated operation and needs approval; if it is not approved, the claim is uncheckable, not confirmed.
3. Service claims: static configuration only. No service is started to check a claim about it.
4. Environment-variable claims: record the references found in configuration and code. Do not read .env files — they may contain secrets and are excluded from this audit.
5. Produce the table: claim number, section, claim text, evidence, verdict (CONFIRMED / CONTRADICTED / UNCHECKABLE), and for contradictions the actual state.

## PASS CRITERIA

Every claim is enumerated and given a verdict; contradictions are stated with the actual state; and no claim is confirmed without evidence separate from the document.

In addition, and without exception: positive control passed, negative control passed, mutation control passed where applicable, independent oracle used, target hash unchanged across the run, and no unresolved evidence capable of changing the conclusion. If such evidence exists the verdict is `UNVERIFIED`, not `PASS`.

## PASS_WITH_WARNINGS CRITERIA

A minority of claims are uncheckable offline and are individually named.

Every warning is named with its own evidence. A warning is not a place to put doubt about the main conclusion — that belongs in `UNVERIFIED`.

## FAIL CRITERIA

A claim that directs behaviour is contradicted by the machine — for example a path that does not exist, or a service configuration that differs.

## BLOCKED CRITERIA

The file cannot be read.

A blocked audit is a legitimate and complete outcome. State precisely what is missing and what would unblock it. Never soften BLOCKED into PASS or into a partial pass.

## UNVERIFIED CRITERIA

A material share of claims requires running tools for which approval was not given.
