## OBJECTIVE

Identify the exact check-digit scheme the implementation is supposed to compute, then verify it against the official formula and independent vectors.

## WHY THIS MATTERS

ISO 7064 is a family, not an algorithm. Mod 11,10 and Mod 97,10 and Mod 11-2 are different computations producing different check digits for the same input. An implementation that is correct for one and applied as another is wrong in a way that looks right on most inputs and fails on a minority — which is the hardest defect to find and the easiest to ship.

## THREAT MODEL

Assuming the variant from the code's shape rather than establishing it from the specification. Testing against values produced by the implementation. Preprocessing differences (stripping separators, handling of a leading zero, the eleventh digit's role) that shift the whole computation.

## STATIC ANALYSIS

No module under `PROJECT_ROOT` may be imported. A top-level import executes code. Parse; do not import.

1. Before any test: identify country, identifier type, exact ISO 7064 variant, modulus, radix, character mapping, check-digit position and preprocessing rules. Record the source for each. If any cannot be established: BLOCKED_SCHEME_IDENTITY_UNCERTAIN, and stop.
2. AST-parse _validate_steuid11 and record the computation verbatim, step by step.
3. Record the identifier's structural constraints from the official specification, separately from the check digit — for the German steuerliche Identifikationsnummer these include digit-repetition rules that are part of validity and are not part of the check digit. Whether the implementation enforces them is a distinct question from whether its check digit is right, and both must be answered.
4. Extract the pattern that feeds the validator and record its length and boundary constructs.
5. Repeat independently for the golden copy.

## RUNTIME TEST MATRIX

Every runtime operation below is gated and requires the human approval token. Nothing here runs before that token arrives.

1. Load the official formula and independent vectors from references/ (REF-03, REF-04). Verify hashes. If absent: BLOCKED. Do not invent vectors and do not use the implementation to produce them.
2. Compute expected check digits independently: once by an implementation written for this audit from the official formula, and once manually for a documented subset.
3. Run the matrix: known-valid identifiers; each with the check digit incremented by one; identifiers violating the structural repetition rules but with a correct check digit; wrong length (10 and 12 digits); with separators; with spaces; with leading and trailing text; empty; None; very long input; all-identical digits.
4. Record per input: matched by pattern, reached the validator, validator result, expected result, agreement.
5. Separate two verdict dimensions: check-digit correctness, and structural validity. Report them separately.

## POSITIVE CONTROL

Known-valid identifiers from the official vectors must validate.

## NEGATIVE CONTROL

Identifiers with a deliberately wrong check digit must fail.

## MUTATION CONTROL

In a sandbox copy, change the modulus or the mapping and confirm every previously valid input now fails. If nothing changes, the validator is not on the measured path.

## INDEPENDENT ORACLE

The official specification of the scheme (REF-03) plus independent vectors (REF-04) plus manual computation. Never the implementation.

Forbidden as an oracle for this audit: the implementation under test, any other copy of it, any project artefact derived from it, any prior report under `docs/`, this package's own reconciliation notes, any output of the failed predecessor package, and model knowledge unsupported by a retrieved source.

## EDGE CASES

- an identifier with the maximum allowed digit repetition
- an identifier where the check digit computes to 0
- an identifier with a leading zero
- an identifier of the right length from a different country's scheme
- a value valid under a different ISO 7064 variant

## PASS CRITERIA

The scheme is identified with a cited official source; all known-valid vectors validate; all known-invalid fail; the mutation control inverts results; and check-digit correctness and structural validity are reported separately.

In addition, and without exception: positive control passed, negative control passed, mutation control passed where applicable, independent oracle used, target hash unchanged across the run, and no unresolved evidence capable of changing the conclusion. If such evidence exists the verdict is `UNVERIFIED`, not `PASS`.

## PASS_WITH_WARNINGS CRITERIA

The check digit is computed correctly and structural rules are not enforced, so structurally impossible identifiers pass. Name it.

Every warning is named with its own evidence. A warning is not a place to put doubt about the main conclusion — that belongs in `UNVERIFIED`.

## FAIL CRITERIA

The implemented variant differs from the official scheme, or a known-valid identifier is rejected, or a known-invalid one accepted.

## BLOCKED CRITERIA

BLOCKED_SCHEME_IDENTITY_UNCERTAIN, or the official formula and vectors are not supplied.

A blocked audit is a legitimate and complete outcome. State precisely what is missing and what would unblock it. Never soften BLOCKED into PASS or into a partial pass.

## REPLICATION REQUIREMENT

```text
replications = 2
phases: RUN-A · RUN-B · COMPARISON
```

Four requirements, stated here explicitly rather than left to be inferred:

1. **RUN-A and RUN-B must use independent methods.** Suggested split: RUN-A implements the official formula from the specification and computes expected values; RUN-B uses only published vectors and manual computation and writes no implementation. Running the same command twice is one method run twice and does not satisfy this requirement.
2. **RUN-B receives no RUN-A conclusion or result material.** No findings, no verdict, no self-critique, no disproof attempt, no expected conclusion — and no path that points at any of them. Both runs receive only: `00_COMMON_RULES.md`, this specification, target identity, target hash, minimal Discovery evidence, and independent oracle material.
3. **COMPARISON occurs only after both runs are sealed.** A comparison drawn before both seals exist compares one run against nothing, and the controller refuses that ordering.
4. **Method disagreement never becomes PASS automatically.** A disagreement between the two runs is a finding in its own right, and is never resolved by preferring the run that matches expectation.
