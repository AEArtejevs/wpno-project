## TITLE

## RISK

HIGH

## OBJECTIVE

Enumerate every version of the TOC exporter that exists on this machine, hash each, and prove from execution-path evidence which one is productive — or prove that it cannot be proven.

## WHY THIS MATTERS

Three files with nearly identical names differ by one byte in size between two of them. Selecting the wrong one means every subsequent audit of 'the exporter' audits a file nobody runs. This project's own CLAUDE.md § 10 names duplicate copies as the root cause of its worst incident: one copy was fixed, the others stayed quietly old.

## TARGET IDENTIFICATION RULE

Re-derive the target set yourself; do not adopt the binding's list as the enumeration. Then compare your enumeration against the binding. A file present in one and not the other is a finding before anything else proceeds.

Hash every candidate with `SHA256_FILE` and compare against the binding. Any mismatch means the tree changed since the package was built: stop and return `BUILD_CONTAMINATED_SOURCE_CHANGED`.

Production identity requires execution-path evidence — an import, an invocation in a script, a container command, a workflow node, a scheduler entry. Filename, version suffix, modification time, file size, documentation, comments and proximity to another file are **excluded by rule**. If production identity cannot be proven, say so; do not nominate a most-likely candidate.

## PRODUCTION PATH REQUIREMENT

State, as a separate recorded item, whether the target is on the production execution path, and on what evidence.

This machine has no runtime supervisor for most audited components: the only two WPNO LaunchAgents are an MCP health poller and a wiki ingest watcher whose watch path is outside `PROJECT_ROOT`, and the only container mounting WPNO source mounts four named files under `docker/litellm`. Everything else in scope is invoked by hand from a shell. Consequently 'productive' is frequently unprovable here, and `BLOCKED_TARGET_IDENTITY_UNCERTAIN` or `UNVERIFIED` is the correct answer rather than a qualified guess.

If the audit proceeds against a candidate rather than a proven productive copy, every conclusion must carry that qualification in its own text — not only in a footnote.

## THREAT MODEL

Choosing the productive copy by the highest version suffix, the newest mtime, the largest size, or a comment. Every one of those is documentation, not evidence. A one-byte size difference between the unnumbered file and v2 is exactly the trap.

## STATIC ANALYSIS

No module under `PROJECT_ROOT` may be imported. A top-level import executes code. Parse; do not import.

1. LIST_DIRECTORY authoring/ and identify every file whose name contains export_with_toc.
2. SHA256_FILE each. Compare against the hashes in this audit's binding; a mismatch means the tree changed since the build and the run stops.
3. Search PROJECT_ROOT for imports and textual references to each version: COUNT_TEXT_MATCHES over source, shell scripts, compose files, Dockerfiles, n8n workflow JSON, MCP configuration and LaunchAgent definitions.
4. PYTHON_AST_PARSE each version. Diff their function sets, their arguments, their constants, and their output paths.
5. Establish whether v3 ever existed: search the Discovery hash inventory, and use GIT_LOG_READONLY and GIT_SHOW_READONLY over authoring/ for a deleted file of that name.
6. Record explicitly, as evidence, every place searched and found empty.

## RUNTIME TEST MATRIX

Every runtime operation below is gated and requires the human approval token. Nothing here runs before that token arrives.

1. No execution of the exporters is required to answer the identity question and none should be performed for it.
2. If, and only if, a caller is found, follow it: read the caller, establish which path it invokes, and hash that path.
3. GIT_LOG_READONLY on authoring/ to date each version's introduction. Dates are context, never proof of production.

## PASS CRITERIA

Not attainable unless execution-path evidence uniquely identifies one version. If it does: that version is named, hashed, and the evidence chain is recorded.

In addition, and without exception: positive control passed, negative control passed, mutation control passed where applicable, independent oracle used, target hash unchanged across the run, and no unresolved evidence capable of changing the conclusion. If such evidence exists the verdict is `UNVERIFIED`, not `PASS`.

## PASS_WITH_WARNINGS CRITERIA

One version is identified as productive with evidence that is real but indirect (for example a wrapper script), and the indirection is named.

Every warning is named with its own evidence. A warning is not a place to put doubt about the main conclusion — that belongs in `UNVERIFIED`.

## FAIL CRITERIA

Evidence shows two different versions are both invoked from different production paths — that is a live inconsistency, not an ambiguity.

## BLOCKED CRITERIA

BLOCKED_TARGET_IDENTITY_UNCERTAIN. This is the expected verdict: this build found no caller for any version. It must be re-established independently, not inherited.

A blocked audit is a legitimate and complete outcome. State precisely what is missing and what would unblock it. Never soften BLOCKED into PASS or into a partial pass.
