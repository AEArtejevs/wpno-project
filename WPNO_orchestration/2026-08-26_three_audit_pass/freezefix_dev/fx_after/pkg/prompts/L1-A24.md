## OBJECTIVE

Establish which instruction files are actually loaded when Claude Code runs from a directory outside `PROJECT_ROOT`, and record the version that produced that behaviour.

## WHY THIS MATTERS

Rules that only apply inside one directory are not rules; they are a local convention. If the project's instructions silently do not load elsewhere, work started from another directory proceeds without them, and nothing in the session indicates that.

## THREAT MODEL

Relying on documentation about loading behaviour rather than observing it. Testing from a directory that is still inside the project tree and concluding about outside. Modifying user configuration to make the test easier, which changes the thing being measured.

There is one further failure mode, and it is the reason this section of the specification was rewritten. The predecessor package required a single directory to be simultaneously below the audit work directory and outside the project. Level-1 lives inside the project, so every audit work directory is inside the project, and no such directory exists. An audit whose scope cannot be satisfied is never performed, and a specification that cannot be satisfied is a defect in the specification rather than in the machine.

## LAUNCH DIRECTORY AND WRITE TOPOLOGY

Two directories are involved, and they are two different directories:

**The launch working directory** is an existing, operator-approved directory outside `PROJECT_ROOT`. It is the directory Claude Code is started from, because 'outside the project' is precisely the condition under test. No file is written to the external working directory — not a temporary file, not a cache, not a log, not an instruction file. Its contents are evidence and must survive the test byte-for-byte.

**The audit work directory** is `work/L1-A24/<RUN-ID>/` inside `LEVEL1_ROOT`. Everything the test produces goes here.

The launch working directory is outside PROJECT_ROOT and is never inside LEVEL1_ROOT; the audit's work directory is inside LEVEL1_ROOT and is never the launch working directory.

To keep the external directory untouched while still capturing what the run produces, every writable location the process would otherwise use is redirected below the audit work directory before the process starts:

```text
HOME                 -> work/L1-A24/<RUN-ID>/home/
TMPDIR               -> work/L1-A24/<RUN-ID>/tmp/
XDG_CACHE_HOME       -> work/L1-A24/<RUN-ID>/cache/
XDG_CONFIG_HOME      -> work/L1-A24/<RUN-ID>/config/
XDG_STATE_HOME       -> work/L1-A24/<RUN-ID>/state/
any tool-specific cache or configuration directory the recorded version uses
                     -> work/L1-A24/<RUN-ID>/
```

Redirecting `HOME` has a consequence that must be stated rather than discovered: with `HOME` redirected, the real user-level instruction file is no longer at the redirected `~`. That is intentional. The run therefore has two parts — one with `HOME` redirected, which measures project-file participation in isolation, and one in which the user-level file is made available inside the redirected home as a byte-identical copy whose hash is recorded, which measures precedence. Which part produced which observation is recorded per observation. A precedence conclusion drawn from the first part alone would be wrong.

No user Claude configuration is created, modified or deleted. The real user configuration directory is read to hash the instruction file and for nothing else.

The external working directory is not named in this specification and must not be. It is bound by the operator before execution, recorded in the plan, and hashed before and after.

## STATIC ANALYSIS

No module under `PROJECT_ROOT` may be imported. A top-level import executes code. Parse; do not import.

1. Record the Claude Code version. Behaviour is version-specific and a result without a version is not reproducible.
2. Identify every instruction file that could participate: the project file, the user-level file at `~/.claude/CLAUDE.md`, and any parent-directory file between the launch directory and the filesystem root.
3. Record each file's path and hash without modifying any of them.
4. Record the operator-approved launch working directory for every test to be performed, together with its pre-run metadata: a recursive listing with sizes, modification times, and a SHA-256 manifest of every file in it.

## RUNTIME TEST MATRIX

Every runtime operation below is gated and requires the human approval token. Nothing here runs before that token arrives. This test additionally requires explicit human approval of the external working directory itself, recorded in the plan, because the operator is asserting that the directory may be used.

1. This requires CLAUDE_LOAD_BEHAVIOUR_TEST, a gated operation. Without approval: BLOCKED. The controller does not launch it; the operator performs it under approval and the transcript is imported as evidence.
2. Prepare the redirection targets under `work/L1-A24/<RUN-ID>/` and record the environment actually handed to the process, verbatim.
3. Capture the external working directory's pre-run manifest.
4. Launch from the operator-approved external working directory. Determine which instructions are in force, by a method that reads the session's own state rather than asking the model to self-report from memory. Record the method.
5. Repeat with the launch directory inside `PROJECT_ROOT`, for comparison.
6. Repeat from a directory that is a sibling of `PROJECT_ROOT`, to separate 'outside the project' from 'outside the home directory'.
7. Record for each launch directory: which files loaded, in what precedence, whether the project file participated, and which part of the run (redirected home without the user file, or redirected home with the copied user file) produced the observation.
8. Capture the external working directory's post-run manifest and compare it to the pre-run manifest. Any difference is a stop condition, not a footnote.

## POSITIVE CONTROL

From inside `PROJECT_ROOT`, the project instruction file must be in force. If it is not even there, the test method is measuring something else.

## NEGATIVE CONTROL

From the external directory, a file that certainly cannot apply must not be reported as loaded.

## MUTATION CONTROL

The write-topology control is the mutation control available here: create a file inside the redirected `TMPDIR` and confirm it appears below `work/L1-A24/<RUN-ID>/` and nowhere else, and that the external directory's manifest is unchanged. This proves the redirection is in force rather than assumed. Mutation of the loading behaviour itself is not available, because it would require modifying user configuration, which is forbidden.

## INDEPENDENT ORACLE

The session's observable state, plus the documented precedence rules for the recorded version, plus the two filesystem manifests of the external directory. The model's recollection of what it loaded is not evidence.

Forbidden as an oracle for this audit: the implementation under test, any other copy of it, any project artefact derived from it, any prior report under `docs/`, this package's own reconciliation notes, any output of the failed predecessor package, and model knowledge unsupported by a retrieved source.

## EDGE CASES

- a launch directory that is a symlink into the project
- a launch directory that is a parent of the project
- a launch directory on a different volume
- a session resumed rather than started
- a directory containing its own instruction file
- a tool that ignores `TMPDIR` and writes to a fixed path — if this occurs, the run stops rather than writing outside the audit work directory

- the target hash changes mid-run → `CONTAMINATED`;
