## OBJECTIVE

Build five synthetic DOCX cases absent from the existing corpus, covering run-split XML text, hidden or alternate text, Unicode homoglyphs, an external relationship reference, and nested or obfuscated instruction text; run them against the filter and record the result.

## WHY THIS MATTERS

The existing corpus covers five vectors (hidden text, white text, tiny font, document properties, footnote). Those are visual concealment. The vectors required here are structural: text that is not visually hidden at all but is split, encoded or referenced in a way that a naive text extractor reassembles differently from a word processor. That gap between what the extractor sees and what the reader sees is where injection lives.

## THREAT MODEL

Instruction text that a text extractor misses but a word processor renders — or the reverse, text the extractor sees that the reader never does. Either mismatch means the filter is inspecting a different document than the one that will be read.

## STATIC ANALYSIS

No module under `PROJECT_ROOT` may be imported. A top-level import executes code. Parse; do not import.

1. Enumerate the existing corpus with hashes so novelty can be proven: ap18/korpus_docx contains W1 hidden, W2 white text, W3 tiny font, W4 document properties, W5 footnote, and two clean files.
2. AST-parse the filter. Determine how it extracts text from a DOCX: which parts it reads, whether it concatenates runs, whether it reads headers, footers, footnotes, comments, text boxes and document properties.
3. Every part the filter does not read is a candidate vector. List them before designing the cases.
4. Determine whether the filter resolves or inspects relationships at all.

## RUNTIME TEST MATRIX

Every runtime operation below is gated and requires the human approval token. Nothing here runs before that token arrives.

1. Build all five DOCX files inside the audit work directory using zipfile and hand-written OOXML. Synthetic content only. No client document. No macro. No GUI application. No external relationship is ever resolved — the reference is present in the file and must never be fetched.
2. N1 run-split: the instruction text split across several w:r runs so that no single run contains a matching substring, while the rendered paragraph reads as one sentence.
3. N2 hidden or alternate text: instruction text placed where an alternate-content or fallback branch renders it, distinct from W1's vanish property. State the distinction from W1 explicitly.
4. N3 homoglyphs: the instruction text with Latin characters replaced by visually identical Cyrillic or Greek ones.
5. N4 external relationship: a relationship entry referencing an external target, present in the .rels part. The case tests whether the filter notices the reference. It must never be dereferenced.
6. N5 nested or obfuscated: instruction text inside a nested structure the extractor may not descend into — a table cell inside a text box, or a comment referencing a footnote.
7. For each case record: identifier, construction method, the exact XML fragment, the vector, why it is not a renaming of W1 to W5, and the expected verdict with reasoning.
8. Run all five through the filter. Record argv, exit code, stdout, stderr and the semantic verdict.
9. For each case also record what an independent extractor sees versus what the rendered document would show.

## POSITIVE CONTROL

The plain, unconcealed instruction text in a normal paragraph must be detected. If the base case is missed, the five results mean nothing.

## NEGATIVE CONTROL

A clean document with no instruction text must not be flagged, for each of the five structural forms — a document that is merely run-split, or merely contains a relationship, must not be flagged on structure alone.

## MUTATION CONTROL

For each case the filter detects, alter the payload so it should no longer match and confirm it does not. This proves detection is of the content, not of the structure.

## INDEPENDENT ORACLE

An independent OOXML reader written for this audit which reconstructs the rendered text run by run, plus an explicit statement per case of what a human reader would see.

Forbidden as an oracle for this audit: the implementation under test, any other copy of it, any project artefact derived from it, any prior report under `docs/`, this package's own reconciliation notes, any output of the failed predecessor package, and model knowledge unsupported by a retrieved source.

## EDGE CASES

- text split across runs by a spell-check boundary
- a homoglyph in only one character of the payload
- a relationship marked external but with an internal-looking target
- instruction text in the document properties and in the body simultaneously
- a DOCX that is a valid ZIP but has a non-standard part order
