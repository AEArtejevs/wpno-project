## TITLE

Output-guard regression from v1 to v3

## RISK

```text
CRITICAL
```

## OBJECTIVE

Run every known-bad case that v1 detects against v3, and identify every protection lost, every false positive introduced, and every false negative introduced between the versions.

## WHY THIS MATTERS

Guardrails are rewritten to reduce noise. Noise reduction removes rules. A rule removed for being noisy is indistinguishable, in the release notes, from a rule removed by accident. The only way to know which happened is to replay the old rule set's detections against the new code.

## THREAT MODEL

A silently dropped rule. A pattern narrowed to fix one false positive that also stopped matching a real case. An existing regression test suite that exercises v1 or v2 while claiming to cover v3.

## STATIC ANALYSIS

No module under `PROJECT_ROOT` may be imported. A top-level import executes code. Parse; do not import.

1. v1 and v2 have a .py.txt extension and are not importable as modules. Copy them into the audit work directory under a .py name. Record the copy's hash and confirm it equals the original's. Never rename or copy anything inside PROJECT_ROOT.
2. PYTHON_AST_PARSE all three. Enumerate for each: rule identifiers, regex patterns, literal constants, thresholds, and the conditions producing a rejection.
3. Produce a rule-level diff v1 -> v2 -> v3: rules present in v1 and absent in v3; rules whose pattern changed; rules added.
4. For every changed pattern, record the old and the new pattern verbatim, and construct the input set on which they differ.
5. Examine any existing regression test in the tree: does it import v3, or an older version? A regression test that exercises the wrong version is itself a finding, and must not be trusted merely because it is green.

## RUNTIME TEST MATRIX

Every runtime operation below is gated and requires the human approval token. Nothing here runs before that token arrives.

1. Build the v1 known-bad corpus: one isolating input per v1 rule, constructed by this audit from the v1 pattern set. All synthetic.
2. Run the full corpus against the v1 sandbox copy. Record detections.
3. Run the identical corpus against v3. Record detections.
4. Build the difference table: detected by v1 and not by v3 (lost protection); detected by v3 and not by v1 (added protection).
5. Build a known-good corpus of legitimate content and run it against both. Detections here are false positives; compare the rates.
6. For every lost protection, state whether the omission is explained by an intentional narrowing visible in the code, or is unexplained. Unexplained loss is the serious result.

## POSITIVE CONTROL

Each isolating input must be detected by the version whose rule it targets. If v1 does not detect its own rule's input, the corpus is wrong, not the guard.

## NEGATIVE CONTROL

The known-good corpus must produce no detections in v1. If v1 flags legitimate content, the false-positive comparison needs that baseline recorded before v3 is judged.

## MUTATION CONTROL

Take one rule present in both v1 and v3, neutralise it in the v3 sandbox copy, and confirm the corresponding input stops being detected. This proves the corpus-to-rule mapping is real.

## INDEPENDENT ORACLE

The AST-extracted rule sets themselves, and inputs constructed from them. Neither guard version validates the other; the corpus is derived from the patterns, not from either guard's output.

Forbidden as an oracle for this audit: the implementation under test, any other copy of it, any project artefact derived from it, any prior report under `docs/`, this package's own reconciliation notes, any output of the failed predecessor package, and model knowledge unsupported by a retrieved source.

## PASS CRITERIA

Every v1 known-bad case is detected by v3; no false negative is introduced; any new false positives are enumerated and explained by an intentional, visible change.

In addition, and without exception: positive control passed, negative control passed, mutation control passed where applicable, independent oracle used, target hash unchanged across the run, and no unresolved evidence capable of changing the conclusion. If such evidence exists the verdict is `UNVERIFIED`, not `PASS`.

## PASS_WITH_WARNINGS CRITERIA

v3 detects everything v1 detected, and introduces false positives that are enumerated and traceable to a specific widened pattern.

Every warning is named with its own evidence. A warning is not a place to put doubt about the main conclusion — that belongs in `UNVERIFIED`.

## FAIL CRITERIA

Any v1 detection is absent in v3 without an explanation visible in the code. Each lost protection is a separate finding with its rule identifier and its isolating input.

## BLOCKED CRITERIA

v1 or v2 cannot be parsed at all, or the copy-to-.py step cannot be performed without writing into PROJECT_ROOT.

A blocked audit is a legitimate and complete outcome. State precisely what is missing and what would unblock it. Never soften BLOCKED into PASS or into a partial pass.

## UNVERIFIED CRITERIA
