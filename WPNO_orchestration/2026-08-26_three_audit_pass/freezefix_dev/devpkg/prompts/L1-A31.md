## TITLE

Full certificate-chain verification without -noverify

## RISK


## OBJECTIVE

Build and verify the complete certificate chain from leaf to trust anchor at a stated validation time, with key usage, extended key usage, signature algorithms, signer identity mapping and revocation status where evidence exists — and without any flag that suppresses verification.

## WHY THIS MATTERS

A parse tells you what a certificate says about itself. Verification tells you whether anyone should believe it. Every suppression flag turns the second into the first while leaving the output looking the same, and an exit code of 0 from a suppressed verification is the single most misleading artefact in this whole domain.

## THREAT MODEL

-noverify, -nosigs, -no_attr_verify, -no_content_verify or -nocerts producing a clean exit that is recorded as a successful verification. An unknown trust anchor treated as trusted. Validation performed at the current time rather than at the signature's claimed time, so an expired certificate appears valid or a valid one appears expired.

## STATIC ANALYSIS

No module under `PROJECT_ROOT` may be imported. A top-level import executes code. Parse; do not import.

1. Locate the certificates in references/ (REF-08, REF-09, REF-11). If leaf, intermediates or trust anchor are absent: the chain cannot be built, and the verdict is UNVERIFIED_TRUST_CHAIN or BLOCKED.
2. OPENSSL_PARSE_CERT each certificate. Mark every parse result PARSE_ONLY_NOT_VERIFICATION.
3. Record per certificate: subject, issuer, serial, NotBefore, NotAfter, key usage, extended key usage, signature algorithm, public key algorithm and size, basic constraints, and the SHA-256 fingerprint.
4. Establish the validation time and justify it: the signature's claimed signing time, a timestamp token if present, or the operator's stated time. Record which was used. Never silently default to now.
5. Build the chain by matching issuer to subject and verifying the authority key identifier against the subject key identifier. Record the chain in order.
6. Identify the trust anchor and its provenance. An anchor that is merely present in the supplied material is not thereby trusted; record where it came from.

## RUNTIME TEST MATRIX

Every runtime operation below is gated and requires the human approval token. Nothing here runs before that token arrives.

1. OPENSSL_VERIFY_CERT_CHAIN with the explicit anchor, the explicit intermediates and the explicit validation time. Record the exact argv, exit code, complete stdout and stderr.
2. The command must contain no suppression flag. If any is present, the result is not evidence of verification and must be labelled PARSE_ONLY_NOT_VERIFICATION.
3. Map the signer identity: which certificate corresponds to which SignerInfo, by issuer-and-serial or by subject key identifier. Record the mapping.
4. Revocation: if CRL or OCSP evidence is supplied (REF-10), check against it and record the result. If not supplied, report revocation as NOT_ASSESSED_OFFLINE. Never report 'not revoked' on the basis of having no evidence.
5. Record every certificate fingerprint in the evidence.

## POSITIVE CONTROL

Verify a chain known to be valid — a self-constructed test chain built in the sandbox — and confirm the command reports success. This proves the verification path works and is not failing for environmental reasons.

## NEGATIVE CONTROL

Verify a chain known to be invalid — the same test chain with the anchor withheld, or with an expired leaf — and confirm the command fails. This proves the command can fail, which is the whole point.

## MUTATION CONTROL

Alter one byte of the leaf certificate in the sandbox and confirm verification fails. If it still succeeds, the command is not verifying what it appears to verify.

## INDEPENDENT ORACLE

An independently constructed test chain built in the sandbox, whose expected verification outcome is known by construction. The artefact under audit is never its own oracle, and neither is a prior report.

Forbidden as an oracle for this audit: the implementation under test, any other copy of it, any project artefact derived from it, any prior report under `docs/`, this package's own reconciliation notes, any output of the failed predecessor package, and model knowledge unsupported by a retrieved source.

## EDGE CASES

- a leaf valid at signing time and expired now
- an intermediate that expired before the leaf
- a chain requiring a cross-certificate
- a certificate whose extended key usage does not include the purpose in question
- an anchor present in the material but not in any recognised trust list
- a signature algorithm now considered weak

## PASS CRITERIA

A complete chain from leaf to a provenanced trust anchor verifies at a justified validation time, with no suppression flag, with key usage and extended key usage satisfied, and with revocation either checked or explicitly reported as not assessed offline.

In addition, and without exception: positive control passed, negative control passed, mutation control passed where applicable, independent oracle used, target hash unchanged across the run, and no unresolved evidence capable of changing the conclusion. If such evidence exists the verdict is `UNVERIFIED`, not `PASS`.

## PASS_WITH_WARNINGS CRITERIA

The chain verifies and revocation could not be assessed offline; state that explicitly rather than implying it was checked.

Every warning is named with its own evidence. A warning is not a place to put doubt about the main conclusion — that belongs in `UNVERIFIED`.

## FAIL CRITERIA

Verification fails, or the chain cannot be built to a trusted anchor, or any suppression flag was needed to obtain a success.

## BLOCKED CRITERIA

Certificates are not supplied. This is the expected verdict today.

A blocked audit is a legitimate and complete outcome. State precisely what is missing and what would unblock it. Never soften BLOCKED into PASS or into a partial pass.

## UNVERIFIED CRITERIA

UNVERIFIED_TRUST_CHAIN — a chain exists but the anchor's provenance cannot be established.

## REPLICATION REQUIREMENT

```text
replications = 2
phases: RUN-A · RUN-B · COMPARISON
```

Four requirements, stated here explicitly rather than left to be inferred. The predecessor package described this audit's replication in prose that never used the words its own self-test required, and the package failed its verification on that sentence. The requirements were never in doubt; only their statement was.

1. **RUN-A and RUN-B must use independent methods.** Suggested split: RUN-A verifies with the openssl command-line under the allowlisted operations; RUN-B builds and checks the chain independently by parsing the ASN.1 structures and verifying each signature step with a standard-library method, without invoking the same command-line path. Running the same command twice is one method run twice and does not satisfy this requirement.
2. **RUN-B receives no RUN-A conclusion or result material.** No findings, no verdict, no self-critique, no disproof attempt, no expected conclusion — and no path that points at any of them. Both runs receive only: `00_COMMON_RULES.md`, this specification, target identity, target hash, minimal Discovery evidence, and independent oracle material.
3. **COMPARISON occurs only after both runs are sealed.** A comparison drawn before both seals exist compares one run against nothing, and the controller refuses that ordering.
4. **Method disagreement never becomes PASS automatically.** A disagreement between the two runs is a finding in its own right, and is never resolved by preferring the run that matches expectation.

None of the cryptographic requirements above is reduced by this restatement: the chain must still be built to a provenanced anchor, at a justified validation time, with no suppression flag, in both runs.
