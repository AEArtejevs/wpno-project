## OBJECTIVE

Design five edge cases that do not exist in any current test file, covering Unicode, punctuation, whitespace, line breaks, and homoglyphs or mixed encoding; run them against the productive guard; record what it does.

## WHY THIS MATTERS

An existing test suite encodes what its author already thought of. Its passing rate measures the author's imagination, not the guard's coverage. New cases are the only way to find the boundary, and a case that is a renamed copy of an existing fixture finds nothing.

## THREAT MODEL

Evasion by representation: the same forbidden content written so that a byte-level or naive-regex rule does not see it, while a human reader sees it perfectly well. Conversely, over-matching on legitimate text that merely resembles the forbidden pattern.

## STATIC ANALYSIS

No module under `PROJECT_ROOT` may be imported. A top-level import executes code. Parse; do not import.

1. Enumerate the existing test corpus so novelty can be proven: read every test file that exercises the guard and list its cases with hashes.
2. PYTHON_AST_PARSE the guard and extract the pattern set, the flags in force (IGNORECASE, UNICODE, MULTILINE, DOTALL), and any normalisation the guard applies before matching (case folding, whitespace collapsing, homoglyph folding).
3. Normalisation that already exists narrows the space of useful cases. Design against what the guard does not normalise.

## RUNTIME TEST MATRIX

Every runtime operation below is gated and requires the human approval token. Nothing here runs before that token arrives.

1. Construct exactly five cases in the audit work directory. All synthetic. For each, record: the case identifier, the exact bytes (hex where not printable), the vector it exercises, why it is not a renaming of an existing fixture, and the expected verdict with the reason.
2. C1 Unicode: the forbidden content expressed with a canonically-equivalent but differently-encoded sequence (for example a precomposed character versus base plus combining mark).
3. C2 Punctuation: the forbidden content interrupted by punctuation that a human reads through — a soft hyphen, a zero-width joiner, a period between characters.
4. C3 Whitespace: non-breaking space, narrow no-break space, and a tab substituted for the space the pattern expects.
5. C4 Line breaks: the forbidden content split across a line break, with CRLF and with LF, and across a paragraph boundary.
6. C5 Homoglyphs or mixed encoding: Cyrillic or Greek characters visually identical to Latin ones, and a mixed-script token.
7. Run all five against the productive guard. Record argv, exit code, stdout, stderr and the semantic verdict for each.
8. For every case the guard misses, state whether the miss is a real evasion or an acceptable limit, and give the reasoning.

## POSITIVE CONTROL

The unmodified forbidden content must be detected. Every case is a variation on it, so if the base case is missed the five results are uninterpretable.

## NEGATIVE CONTROL

Legitimate text containing the same characters in an innocent arrangement must not be detected. Each of the five vectors gets its own negative counterpart.

## MUTATION CONTROL

For each case the guard detects, alter one character so it should no longer match, and confirm it does not. This proves detection is specific rather than incidental.

## INDEPENDENT ORACLE

A human-readable rendering of each case plus an explicit statement of what a reader sees. The claim 'a reader would read this as the forbidden content' is the oracle, and it is stated per case rather than assumed.

Forbidden as an oracle for this audit: the implementation under test, any other copy of it, any project artefact derived from it, any prior report under `docs/`, this package's own reconciliation notes, any output of the failed predecessor package, and model knowledge unsupported by a retrieved source.

## EDGE CASES

- combining marks in a different order
- overlong or invalid UTF-8
- BOM in the middle of a document
- right-to-left override characters
- content inside a DOCX field code rather than a run

## REGRESSION REQUIREMENTS

The five cases, their bytes, and the guard's verdict for each become a permanent suite.

Record it in the audit's evidence directory in a form a later run can replay without reconstruction.

## PASS CRITERIA

All five cases are novel with respect to the existing corpus; all five were run; the positive and negative controls hold; and every miss is classified with reasoning.

In addition, and without exception: positive control passed, negative control passed, mutation control passed where applicable, independent oracle used, target hash unchanged across the run, and no unresolved evidence capable of changing the conclusion. If such evidence exists the verdict is `UNVERIFIED`, not `PASS`.

## PASS_WITH_WARNINGS CRITERIA

The guard misses cases that are classified, with reasoning, as acceptable limits rather than evasions.

Every warning is named with its own evidence. A warning is not a place to put doubt about the main conclusion — that belongs in `UNVERIFIED`.

## FAIL CRITERIA

The guard misses a case that is a genuine evasion — the forbidden content is plainly readable and passes.

## BLOCKED CRITERIA

The guard cannot be run, or the existing corpus cannot be enumerated so novelty cannot be proven.

A blocked audit is a legitimate and complete outcome. State precisely what is missing and what would unblock it. Never soften BLOCKED into PASS or into a partial pass.

## UNVERIFIED CRITERIA

Cases were run but the guard's verdict could not be attributed to a rule.
