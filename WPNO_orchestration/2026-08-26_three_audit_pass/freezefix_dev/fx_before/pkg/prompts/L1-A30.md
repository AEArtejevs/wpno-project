## OBJECTIVE

Detect AppleDouble and macOS metadata artefacts in the archive by raw listing and central-directory inspection, and determine what, if anything, their presence implies about the signed content.

## WHY THIS MATTERS

A macOS copy operation adds __MACOSX entries and ._ files to an archive. Their presence proves the archive passed through a macOS tool. It does not, on its own, prove the signed content changed — and the leap from the first to the second is the error this audit exists to prevent.

## THREAT MODEL

Equating AppleDouble presence with corruption of signed content. The reverse error: dismissing the entries as cosmetic without checking whether they fall inside the signature's coverage. Detecting entries only in an extracted view, where the extraction tool may have already discarded or created them.

## STATIC ANALYSIS

No module under `PROJECT_ROOT` may be imported. A top-level import executes code. Parse; do not import.

1. Locate the archive in references/ (REF-11). If absent: BLOCKED. Note that the only occurrence of the string AppleDouble anywhere in PROJECT_ROOT is in S7_bestand.sh, an unrelated inventory script; it is not this audit's target and must not be bound as one.
2. ZIP_LIST the archive without extracting. Record the complete entry list.
3. Inspect the central directory entries directly, not only the listing summary: names, order, sizes, external attributes, and any entries a normal listing omits.
4. Search the entry names for __MACOSX prefixes, ._ prefixes on basenames, .DS_Store, and Icon entries.
5. Record path normalisation: an entry name may differ in Unicode normal form between the archive and the filesystem, so a name comparison must state which form it used.

## RUNTIME TEST MATRIX

Every runtime operation below is gated and requires the human approval token. Nothing here runs before that token arrives.

1. If extraction is required and approved (ARCHIVE_EXTRACT_SANDBOX), extract into the audit work directory only, and compare the extracted listing against the raw listing. Differences between them are attributable to the extraction tool and must be recorded as such, not as properties of the archive.
2. For every metadata entry found, determine whether it lies inside or outside the byte range the signature covers. This is the decisive question and it requires the coverage boundary from L1-A34.
3. Report separately: (a) which metadata entries exist; (b) whether they are inside the signature's coverage; (c) what follows for the signed content. Do not collapse these into one statement.

## POSITIVE CONTROL

Construct a synthetic archive known to contain __MACOSX and ._ entries and confirm the method detects them.

## NEGATIVE CONTROL

Construct a synthetic archive with none and confirm the method reports none.

## MUTATION CONTROL

Add a single ._ entry to a synthetic archive and confirm detection. Remove it and confirm non-detection.

## INDEPENDENT ORACLE

The raw central directory read with the standard library's zipfile, independent of any extraction tool.

Forbidden as an oracle for this audit: the implementation under test, any other copy of it, any project artefact derived from it, any prior report under `docs/`, this package's own reconciliation notes, any output of the failed predecessor package, and model knowledge unsupported by a retrieved source.

## EDGE CASES

- a ._ file whose base file is absent
- an entry name differing only in Unicode normalisation
- a __MACOSX entry with a zero-length payload
- metadata entries added after signing
- an archive where the extraction tool silently drops metadata entries

## REGRESSION REQUIREMENTS

Record it in the audit's evidence directory in a form a later run can replay without reconstruction.

## PASS CRITERIA

Detection is performed on the raw archive; every metadata entry is enumerated; and the implication for the signed content is stated with the coverage boundary, without equating presence with corruption.

In addition, and without exception: positive control passed, negative control passed, mutation control passed where applicable, independent oracle used, target hash unchanged across the run, and no unresolved evidence capable of changing the conclusion. If such evidence exists the verdict is `UNVERIFIED`, not `PASS`.

## PASS_WITH_WARNINGS CRITERIA

Metadata entries are present and the coverage boundary is not yet established, so the implication is stated as open.

Every warning is named with its own evidence. A warning is not a place to put doubt about the main conclusion — that belongs in `UNVERIFIED`.

## FAIL CRITERIA

Metadata entries lie inside the signature's coverage and the content therefore differs from what was signed.

## BLOCKED CRITERIA

The archive is not supplied. This is the expected verdict today.

A blocked audit is a legitimate and complete outcome. State precisely what is missing and what would unblock it. Never soften BLOCKED into PASS or into a partial pass.

## UNVERIFIED CRITERIA

Entries are enumerated and the coverage boundary cannot be determined.
