## OBJECTIVE

Establish the complete chain from production entrypoint through caller, gateway or orchestrator, into the input filter, and on to the downstream processor — or establish that the filter is not on that chain.

## WHY THIS MATTERS

A filter that exists, imports cleanly and passes its unit tests protects nothing if the production path does not call it. This is the difference between a control and a file. Existence is not invocation, and a static import is not invocation either: a module can be imported and its filter function never called.

## TARGET IDENTIFICATION RULE

Re-derive the target set yourself; do not adopt the binding's list as the enumeration. Then compare your enumeration against the binding. A file present in one and not the other is a finding before anything else proceeds.

Hash every candidate with `SHA256_FILE` and compare against the binding. Any mismatch means the tree changed since the package was built: stop and return `BUILD_CONTAMINATED_SOURCE_CHANGED`.

Production identity requires execution-path evidence — an import, an invocation in a script, a container command, a workflow node, a scheduler entry. Filename, version suffix, modification time, file size, documentation, comments and proximity to another file are **excluded by rule**. If production identity cannot be proven, say so; do not nominate a most-likely candidate.

## PRODUCTION PATH REQUIREMENT

State, as a separate recorded item, whether the target is on the production execution path, and on what evidence.

This machine has no runtime supervisor for most audited components: the only two WPNO LaunchAgents are an MCP health poller and a wiki ingest watcher whose watch path is outside `PROJECT_ROOT`, and the only container mounting WPNO source mounts four named files under `docker/litellm`. Everything else in scope is invoked by hand from a shell. Consequently 'productive' is frequently unprovable here, and `BLOCKED_TARGET_IDENTITY_UNCERTAIN` or `UNVERIFIED` is the correct answer rather than a qualified guess.

If the audit proceeds against a candidate rather than a proven productive copy, every conclusion must carry that qualification in its own text — not only in a footnote.

## THREAT MODEL

A filter present in the tree and absent from the path. A path that calls the filter but ignores its return value. A path that calls it after the data has already been used. A second, older filter on the real path while the audited one sits unused.

## STATIC ANALYSIS

No module under `PROJECT_ROOT` may be imported. A top-level import executes code. Parse; do not import.

1. Identify every production entrypoint: shell scripts, __main__ blocks, container commands, LaunchAgent programs, workflow nodes, MCP server handlers.
2. For each, follow the call chain statically by AST: imports, function calls, and the argument flow.
3. Search for every reference to AP18_eingangsfilter across source, shell, compose, Dockerfile, workflow JSON, MCP configuration and LaunchAgent plists.
4. Where the filter is imported, determine whether its filtering function is actually invoked, and whether its return value is checked or discarded. An ignored return value is equivalent to no filter.
5. Determine the position of the call relative to the processing: before the data is used, or after.
6. Record the search set exhaustively, including every location searched and found empty, so absence is documented rather than assumed.

## RUNTIME TEST MATRIX

Every runtime operation below is gated and requires the human approval token. Nothing here runs before that token arrives.

1. No execution of the production system is permitted. This is a static chain-of-invocation question and must be answered statically.
2. If a database of prior checks exists (ap18/eingangspruefungen.sqlite), it may be used only via DATABASE_EVIDENCE_IMPORT of an operator-produced export, and only as evidence that the filter ran at some past time — which is not the same as being on the current path.
3. Present the result in the required form: production entrypoint -> caller -> gateway or orchestrator -> input filter -> downstream processor. If a link is missing, show the chain breaking at the exact point.

## PASS CRITERIA

A complete chain from production entrypoint to downstream processor through the filter is demonstrated, and the filter's return value is shown to be acted upon.

In addition, and without exception: positive control passed, negative control passed, mutation control passed where applicable, independent oracle used, target hash unchanged across the run, and no unresolved evidence capable of changing the conclusion. If such evidence exists the verdict is `UNVERIFIED`, not `PASS`.

## PASS_WITH_WARNINGS CRITERIA

The chain exists but the filter is invoked after part of the data has already been processed, or its result only logs rather than blocks.

Every warning is named with its own evidence. A warning is not a place to put doubt about the main conclusion — that belongs in `UNVERIFIED`.

## FAIL CRITERIA

FAIL_FILTER_NOT_IN_PRODUCTION_PATH — the filter exists but the productive execution path bypasses it. Note that this build's reconciliation found no caller at all, so this is the expected outcome. It must be established independently by this audit and not inherited from that note.

## BLOCKED CRITERIA

Production entrypoints cannot be enumerated because configuration is absent.

A blocked audit is a legitimate and complete outcome. State precisely what is missing and what would unblock it. Never soften BLOCKED into PASS or into a partial pass.

## UNVERIFIED CRITERIA

A chain exists partially and the missing link is a runtime dispatch that cannot be resolved statically.
