## TARGET IDENTIFICATION RULE

Re-derive the target set yourself; do not adopt the binding's list as the enumeration. Then compare your enumeration against the binding. A file present in one and not the other is a finding before anything else proceeds.

Hash every candidate with `SHA256_FILE` and compare against the binding. Any mismatch means the tree changed since the package was built: stop and return `BUILD_CONTAMINATED_SOURCE_CHANGED`.

Production identity requires execution-path evidence — an import, an invocation in a script, a container command, a workflow node, a scheduler entry. Filename, version suffix, modification time, file size, documentation, comments and proximity to another file are **excluded by rule**. If production identity cannot be proven, say so; do not nominate a most-likely candidate.

## PRODUCTION PATH REQUIREMENT

State, as a separate recorded item, whether the target is on the production execution path, and on what evidence.

This machine has no runtime supervisor for most audited components: the only two WPNO LaunchAgents are an MCP health poller and a wiki ingest watcher whose watch path is outside `PROJECT_ROOT`, and the only container mounting WPNO source mounts four named files under `docker/litellm`. Everything else in scope is invoked by hand from a shell. Consequently 'productive' is frequently unprovable here, and `BLOCKED_TARGET_IDENTITY_UNCERTAIN` or `UNVERIFIED` is the correct answer rather than a qualified guess.

If the audit proceeds against a candidate rather than a proven productive copy, every conclusion must carry that qualification in its own text — not only in a footnote.

## THREAT MODEL

Reporting 'the copies are identical' without naming the level. Two files can be byte-identical, or AST-identical with different comments, or functionally identical with different regexes that happen to agree on the tested inputs. Each is a different statement and only one of them is usually true.

## STATIC ANALYSIS

No module under `PROJECT_ROOT` may be imported. A top-level import executes code. Parse; do not import.

1. Enumerate every copy from the filesystem and from the Discovery hash inventory. Do not use this prompt's list as the enumeration; produce your own and compare.
2. SHA256_FILE each. Group by hash.
3. COMPARE_BINARY_FILES within and across groups.
4. Normalise source (strip comments, normalise whitespace and line endings) and compare again. Record the normalisation applied.
5. PYTHON_AST_PARSE each and compare the ASTs with docstrings and comments removed.
6. Compare function sets: names, signatures, presence and absence.
7. Compare regex patterns literally, and note that two different patterns can match identically on a given corpus without being equal — say which claim you are making.
8. Compare constants, validation rules and the _VALIDATORS mapping.
9. Compare error handling and control flow.
10. Determine production status per copy: which is bind-mounted, which is a backup by naming convention plus content, which is golden, which is historical.
11. Present a matrix: copy x comparison level, with the result at each level.

## RUNTIME TEST MATRIX

Every runtime operation below is gated and requires the human approval token. Nothing here runs before that token arrives.

1. No execution is required. This audit is a comparison and must be performed statically.
2. Container-side copies may only be hashed from an operator-produced export; the Docker socket is forbidden.

## POSITIVE CONTROL

Two files known to be byte-identical must compare equal at every level. This proves the comparison chain works.

## NEGATIVE CONTROL

Two files known to differ must compare unequal at the raw level. This proves the comparison is not reporting equality indiscriminately.

## MUTATION CONTROL

Copy one file into the sandbox, change a single comment, and confirm: raw differs, normalised source is equal, AST is equal. This proves each level measures what it claims.

## INDEPENDENT ORACLE

SHA-256 and the standard library's ast module, both independent of the code under test.

Forbidden as an oracle for this audit: the implementation under test, any other copy of it, any project artefact derived from it, any prior report under `docs/`, this package's own reconciliation notes, any output of the failed predecessor package, and model knowledge unsupported by a retrieved source.

## EDGE CASES

- two copies differing only in line endings
- two copies differing only in a docstring
- two copies with identical functions in a different order
- a copy with an unused import removed
- a copy whose regex differs but matches identically on the available corpus

## PASS CRITERIA

Every copy is enumerated and hashed; the comparison matrix is complete at every named level; production status per copy is stated with its evidence; and no equality claim is made without naming its level.

In addition, and without exception: positive control passed, negative control passed, mutation control passed where applicable, independent oracle used, target hash unchanged across the run, and no unresolved evidence capable of changing the conclusion. If such evidence exists the verdict is `UNVERIFIED`, not `PASS`.

## PASS_WITH_WARNINGS CRITERIA

The two live copies agree byte-for-byte and the golden copy differs in ways that are enumerated and explained.

Every warning is named with its own evidence. A warning is not a place to put doubt about the main conclusion — that belongs in `UNVERIFIED`.

## FAIL CRITERIA

Two copies both reachable from a production path differ at the level of validation rules, regexes or control flow.

## BLOCKED CRITERIA

Copies cannot be hashed, or a container copy cannot be obtained and its content is material to the conclusion.

A blocked audit is a legitimate and complete outcome. State precisely what is missing and what would unblock it. Never soften BLOCKED into PASS or into a partial pass.

## UNVERIFIED CRITERIA

Some copies exist only inside a container and no export was supplied.
