## STATIC ANALYSIS

No module under `PROJECT_ROOT` may be imported. A top-level import executes code. Parse; do not import.

1. Locate vhn.xml.p7s and the content it covers in references/ (REF-11). If absent: BLOCKED. It does not exist in any Discovery scan root.
2. Establish raw file identity first: canonical path, size, two independent hashes, chain of custody.
3. Determine the structure: CMS or PKCS#7, and the exact content type.
4. Determine encapsulated versus detached. If detached, identify the external content precisely and hash it — the whole verification depends on hashing the right bytes.
5. Enumerate signed attributes for every signer, including contentType, messageDigest and signingTime.
6. Identify the signer certificate for each SignerInfo and the chain, as in L1-A31 and L1-A32.
7. Establish the verification time and justify it. Prefer a verified timestamp token over a self-asserted signingTime, and say which was used.

## RUNTIME TEST MATRIX

Every runtime operation below is gated and requires the human approval token. Nothing here runs before that token arrives.

1. OPENSSL_VERIFY_CMS with the explicit content, the explicit certificates, the explicit anchor and the explicit verification time. Record exact argv, exit code, complete stdout and stderr.
2. No suppression flag anywhere. -noverify, -nosigs, -no_attr_verify, -no_content_verify and -nocerts are forbidden as PASS evidence, and their presence makes the result PARSE_ONLY_NOT_VERIFICATION.
3. Verify content binding explicitly: the messageDigest attribute must equal the digest of the content, and the signature must cover the attribute set that contains it. Both links, separately evidenced. A signature valid over attributes not bound to the content proves nothing about the content.
4. Verify every SignerInfo separately (L1-A32) and report per signer.
5. Verify countersignatures and timestamp tokens separately, each with its own chain.
6. State the coverage boundary explicitly: exactly which bytes the signature covers and which it does not. L1-A30 and L1-A35 both depend on this statement.

## POSITIVE CONTROL

Construct a synthetic signed object in the sandbox whose verification must succeed, and confirm the command reports success. This proves the verification path works.

## NEGATIVE CONTROL

Construct a synthetic signed object whose verification must fail — corrupted signature, or missing anchor — and confirm the command fails with a non-zero exit. A verification path that cannot fail is not a verification path.

## MUTATION CONTROL

Alter one byte of the content in a sandbox copy and re-verify. Verification must fail. If it still succeeds, the signature does not cover the content, and that is the finding.

## INDEPENDENT ORACLE

An independently constructed signed object with a known outcome, plus an independent structural read of the ASN.1. Never the artefact's own claim, never a prior report.

Forbidden as an oracle for this audit: the implementation under test, any other copy of it, any project artefact derived from it, any prior report under `docs/`, this package's own reconciliation notes, any output of the failed predecessor package, and model knowledge unsupported by a retrieved source.

## EDGE CASES

- detached content with a trailing byte difference
- signingTime present and no timestamp token
- a timestamp token whose authority certificate is absent
- two signers where only one verifies
- a signature covering attributes that omit messageDigest
- an algorithm the local library does not support

## REPLICATION REQUIREMENT

```text
replications = 2
phases: RUN-A · RUN-B · COMPARISON
```

Four requirements, stated here explicitly rather than left to be inferred:

1. **RUN-A and RUN-B must use independent methods.** Suggested split: RUN-A verifies with the openssl CMS command-line path; RUN-B performs an independent structural verification — parse the ASN.1, extract the signed attributes, recompute the messageDigest over the content, and verify the signature over the DER-encoded attribute set with a standard-library method. Running the same command twice is one method run twice and does not satisfy this requirement.
2. **RUN-B receives no RUN-A conclusion or result material.** No findings, no verdict, no self-critique, no disproof attempt, no expected conclusion — and no path that points at any of them. Both runs receive only: `00_COMMON_RULES.md`, this specification, target identity, target hash, minimal Discovery evidence, and independent oracle material.
3. **COMPARISON occurs only after both runs are sealed.** A comparison drawn before both seals exist compares one run against nothing, and the controller refuses that ordering.
4. **Method disagreement never becomes PASS automatically.** A disagreement between the two runs is a finding in its own right, and is never resolved by preferring the run that matches expectation.

None of the cryptographic requirements above is reduced by this restatement: content binding, the absence of suppression flags, the per-signer results and the stated coverage boundary are required in both runs.
