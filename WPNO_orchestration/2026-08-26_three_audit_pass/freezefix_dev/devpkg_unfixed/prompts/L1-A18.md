## OBJECTIVE

Verify the Mod-97 implementation against independently computed expected values and independent official test vectors, across at least six countries, with the full malformed-input matrix.

## WHY THIS MATTERS

An IBAN validator inside a PII scanner decides what leaves this system. A validator that is too strict lets real account numbers through unredacted because it decided they were invalid. A validator that is too loose redacts everything that looks numeric and is turned off. Both failures are silent, and both are discovered by an opponent rather than by the operator.

## THREAT MODEL

Using the implementation to generate its own expected values, which validates nothing. A check-digit routine correct for the common case and wrong at a boundary (leading zeros, the 34-character maximum, a country length the routine does not know). A pattern that never reaches the validator at all — this build's static reading suggests the German 'iban' pattern is not registered in _VALIDATORS while 'iban_intl' is, which would mean German IBANs are matched without any Mod-97 check.

## STATIC ANALYSIS

No module under `PROJECT_ROOT` may be imported. A top-level import executes code. Parse; do not import.

1. AST-parse the target. Extract _validate_iban_intl verbatim, and the _VALIDATORS mapping.
2. Determine which patterns are validated and which are not. Record the finding either way — this is the central static question of this audit.
3. Extract both IBAN patterns and record their exact regex, flags and length bounds.
4. Compare the implementation against the ISO 13616 / Mod-97-10 definition step by step: the rearrangement, the letter-to-digit mapping, the modulus, and the expected remainder.
5. Record the length bounds the implementation enforces (15 to 34) and compare against the specification's per-country lengths — a global bound is not a per-country check.
6. Repeat the whole static analysis independently for anonymization/golden/payload_scan.py, which differs.

## RUNTIME TEST MATRIX

Every runtime operation below is gated and requires the human approval token. Nothing here runs before that token arrives.

1. Load official or trusted offline test vectors from references/ (REF-01, REF-02). Verify their hashes. If absent: BLOCKED. Do not invent vectors.
2. Build the country set: at least six, with differing lengths and differing BBAN structures. Every value synthetic or drawn from the official registry's published examples — never a real account.
3. Compute the expected result for every input by an independent Mod-97 implementation written for this audit, AND by manual computation for a documented subset. Two independent methods, neither of them the target.
4. Run the matrix: known-valid per country; known-invalid per country; altered check digits; wrong length for the country; embedded spaces; lowercase; Unicode whitespace including U+00A0 and U+202F; leading and trailing text; empty string; None; a 10 000-character input.
5. Record for every input: matched by pattern (yes/no), reached the validator (yes/no), validator result, expected result, agreement.
6. The 'reached the validator' column is essential. A value that never reaches the validator has no validator result, and recording it as 'valid' would be wrong.

## POSITIVE CONTROL

Known-valid IBANs from the official vectors must validate. If they do not, the implementation is broken outright.

## NEGATIVE CONTROL

Known-invalid IBANs — correct format, wrong check digit — must fail. If they pass, the check digit is not being computed.

## MUTATION CONTROL

In a sandbox copy, change the modulus from 97 to 96 and re-run. Every previously valid input must now fail. If results are unchanged, the validator is not being called on the path being measured.

## INDEPENDENT ORACLE

Official registry test vectors (REF-01, REF-02) plus an independent Mod-97 implementation written for this audit plus manual computation for a subset. The production implementation may never generate an expected value.

Forbidden as an oracle for this audit: the implementation under test, any other copy of it, any project artefact derived from it, any prior report under `docs/`, this package's own reconciliation notes, any output of the failed predecessor package, and model knowledge unsupported by a retrieved source.

## EDGE CASES

- an IBAN of exactly 15 and exactly 34 characters
- a BBAN containing leading zeros
- an all-digit BBAN and an alphanumeric BBAN
- a country code that exists but whose length differs from the input
- a valid IBAN embedded in a longer alphanumeric token
- a valid IBAN split by a line break

## PASS CRITERIA

All known-valid vectors validate; all known-invalid fail; the malformed matrix behaves as specified; the mutation control inverts the results; and the pattern-to-validator mapping is fully documented, including any pattern that bypasses validation.

In addition, and without exception: positive control passed, negative control passed, mutation control passed where applicable, independent oracle used, target hash unchanged across the run, and no unresolved evidence capable of changing the conclusion. If such evidence exists the verdict is `UNVERIFIED`, not `PASS`.

## PASS_WITH_WARNINGS CRITERIA

The Mod-97 computation is correct and the per-country length check is absent, so a structurally wrong but check-digit-valid string passes. Name it.

Every warning is named with its own evidence. A warning is not a place to put doubt about the main conclusion — that belongs in `UNVERIFIED`.

## FAIL CRITERIA

A known-valid IBAN is rejected, a known-invalid one accepted, or a matched pattern reaches no validator while the system treats a match as validated.

## BLOCKED CRITERIA

Official vectors are not supplied. Do not proceed with invented vectors.

A blocked audit is a legitimate and complete outcome. State precisely what is missing and what would unblock it. Never soften BLOCKED into PASS or into a partial pass.

## UNVERIFIED CRITERIA

## REPLICATION REQUIREMENT

```text
replications = 2
phases: RUN-A · RUN-B · COMPARISON
```

Four requirements, stated here explicitly rather than left to be inferred:

1. **RUN-A and RUN-B must use independent methods.** Suggested split: RUN-A derives expected values from an independently written Mod-97 implementation; RUN-B derives them from the official registry vectors plus manual computation, without writing an implementation at all. Running the same command twice is one method run twice and does not satisfy this requirement.
2. **RUN-B receives no RUN-A conclusion or result material.** No findings, no verdict, no self-critique, no disproof attempt, no expected conclusion — and no path that points at any of them. Both runs receive only: `00_COMMON_RULES.md`, this specification, target identity, target hash, minimal Discovery evidence, and independent oracle material.
3. **COMPARISON occurs only after both runs are sealed.** A comparison drawn before both seals exist compares one run against nothing, and the controller refuses that ordering.
4. **Method disagreement never becomes PASS automatically.** A disagreement between the two runs is a finding in its own right, and is never resolved by preferring the run that matches expectation.
