## TITLE

BGH_REGISTER completeness versus an independent official roster

## RISK

```text
HIGH
```

## OBJECTIVE

Compare the register the checker relies on against an independent official roster, and identify missing entries, obsolete entries, spelling and normalisation differences, and role or date validity mismatches.

## WHY THIS MATTERS

A register used to decide whether a citation is plausible determines which citations are examined and which pass unexamined. If the register is incomplete, the checker's silence on a citation means nothing. A register validated against itself is validated against nothing.

## THREAT MODEL

Circular validation — checking the register against another project artefact derived from the same source. Silent staleness, where the register was correct when written and the roster has since changed. Normalisation mismatches that make a present entry look absent.

## STATIC ANALYSIS

No module under `PROJECT_ROOT` may be imported. A top-level import executes code. Parse; do not import.

1. Extract BGH_REGISTER from the checker by AST parse. Record every entry verbatim, its structure, and any date or role fields.
2. Record the register's own claimed period of validity if it states one. If it states none, that absence is a finding: a roster without a validity period cannot be checked for staleness.
3. Record how the checker normalises an entry before comparison (case, whitespace, punctuation, titles), because normalisation determines what counts as a match.
4. Record explicitly that bgh_referenz.json is a project artefact and is excluded as an oracle.

## RUNTIME TEST MATRIX

Every runtime operation below is gated and requires the human approval token. Nothing here runs before that token arrives.

1. Locate the operator-supplied official roster in references/ (REF-05). Verify its SHA-256 against references/manifest.json before use.
2. If no official roster is present: stop and return BLOCKED_MISSING_OFFICIAL_REFERENCE. Do not substitute model knowledge. Do not use bgh_referenz.json. Do not reach the network.
3. Parse the roster into a comparable structure using standard-library parsing only, with external entities and DTD disabled.
4. Compute four sets: present in both; in the register but not the roster (obsolete); in the roster but not the register (missing); present in both but differing in spelling, normalisation, role or date validity.
5. Report the fourth set separately from the first — a near-match is not a match, and treating it as one is how staleness hides.

## POSITIVE CONTROL

Take one entry known to be in both, and confirm the comparison reports it as matched. This proves the comparison can see agreement.

## NEGATIVE CONTROL

Insert a fabricated name into the comparison input and confirm it is reported as present-in-register-only. This proves the comparison can see disagreement.

## MUTATION CONTROL

Alter one character of a matched entry and confirm it moves from the matched set to the differing set rather than silently remaining matched.

## INDEPENDENT ORACLE

The operator-supplied official roster (REF-05) and nothing else. Neither BGH_REGISTER, nor bgh_referenz.json, nor any docs/ report, nor model knowledge.

Forbidden as an oracle for this audit: the implementation under test, any other copy of it, any project artefact derived from it, any prior report under `docs/`, this package's own reconciliation notes, any output of the failed predecessor package, and model knowledge unsupported by a retrieved source.

## EDGE CASES

- names with umlauts in composed and decomposed forms
- names with academic titles present in one source and not the other
- double-barrelled surnames
- an official whose role changed during the period
- an entry valid only for part of the period

## PASS CRITERIA

An official roster was used; all four sets are computed; missing, obsolete and differing entries are enumerated; and the controls hold.

In addition, and without exception: positive control passed, negative control passed, mutation control passed where applicable, independent oracle used, target hash unchanged across the run, and no unresolved evidence capable of changing the conclusion. If such evidence exists the verdict is `UNVERIFIED`, not `PASS`.

## PASS_WITH_WARNINGS CRITERIA

The comparison is complete but the roster's period does not fully cover the register's claimed period; state the uncovered span.

Every warning is named with its own evidence. A warning is not a place to put doubt about the main conclusion — that belongs in `UNVERIFIED`.

## FAIL CRITERIA

The register is missing entries present in the official roster, or contains entries the roster does not support, in a way that would change a citation verdict.

## BLOCKED CRITERIA

BLOCKED_MISSING_OFFICIAL_REFERENCE — no offline official source is present. This is the expected verdict today.

A blocked audit is a legitimate and complete outcome. State precisely what is missing and what would unblock it. Never soften BLOCKED into PASS or into a partial pass.
