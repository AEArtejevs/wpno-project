## OBJECTIVE

Identify the exact archive, hash its raw bytes with at least two independent methods, and record size, mtime and canonical path with the raw evidence preserved.

## WHY THIS MATTERS

Every downstream claim about this archive depends on the hash being a hash of the archive as it exists, not of a reconstruction of it. Unpacking and repacking produces a different file with the same contents and a different hash — and the difference is invisible in any listing.

## THREAT MODEL

## RUNTIME TEST MATRIX

Every runtime operation below is gated and requires the human approval token. Nothing here runs before that token arrives.

1. Hash the raw archive bytes. Do not open it, do not extract it, do not normalise it first.
2. Method 1: SHA256_FILE via the allowlisted operation.
3. Method 2: an independent computation — a different tool or a standard-library streaming hash written for this audit, reading the file in binary.
4. Both must agree. A disagreement means one method is not reading the raw bytes and must be resolved before anything else.
5. Also record a second algorithm (for example SHA-512) so a later comparison is not dependent on one algorithm.
6. Preserve the raw evidence: the hashes, the byte count, the file metadata, and the exact commands, in the audit evidence directory. Never copy the archive itself into the report.

## POSITIVE CONTROL

Hash a file of known content whose hash is independently known, and confirm both methods produce it. This proves both methods are correct.

## NEGATIVE CONTROL

Hash two files known to differ and confirm the hashes differ.

## MUTATION CONTROL

Copy the archive into the sandbox, alter one byte, and confirm both methods detect the change. This proves the measurement resolves a single-byte difference.

## INDEPENDENT ORACLE

Two independent hashing methods, and the file's own byte count. Neither method may be derived from the other.

Forbidden as an oracle for this audit: the implementation under test, any other copy of it, any project artefact derived from it, any prior report under `docs/`, this package's own reconciliation notes, any output of the failed predecessor package, and model knowledge unsupported by a retrieved source.

## EDGE CASES

- an archive with a trailing comment after the central directory
- an archive with prepended bytes (a self-extracting stub)
- an archive whose size is reported differently by the filesystem and the central directory
- a sparse file
- a file still being written

## PASS CRITERIA

The archive is identified; two independent methods agree; the raw bytes were hashed without any intermediate unpacking; metadata and custody are recorded.

In addition, and without exception: positive control passed, negative control passed, mutation control passed where applicable, independent oracle used, target hash unchanged across the run, and no unresolved evidence capable of changing the conclusion. If such evidence exists the verdict is `UNVERIFIED`, not `PASS`.

## PASS_WITH_WARNINGS CRITERIA

Hashes agree and the chain of custody has a gap that is stated.

Every warning is named with its own evidence. A warning is not a place to put doubt about the main conclusion — that belongs in `UNVERIFIED`.

## FAIL CRITERIA

The two methods disagree, or the file that was hashed cannot be shown to be the archive in question.

## BLOCKED CRITERIA

The archive is not supplied. This is the expected verdict today.

A blocked audit is a legitimate and complete outcome. State precisely what is missing and what would unblock it. Never soften BLOCKED into PASS or into a partial pass.

## UNVERIFIED CRITERIA

The archive is supplied without a chain of custody, so the hash is of a file whose provenance is unknown.
