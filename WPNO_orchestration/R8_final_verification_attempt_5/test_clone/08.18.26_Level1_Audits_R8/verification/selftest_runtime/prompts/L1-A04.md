## TITLE

Table of contents versus actual generated document text

## RISK

```text
HIGH
```

## OBJECTIVE

Compare the generated table of contents against the headings that are actually present in the generated document, extracted independently of the generator.

## WHY THIS MATTERS

The natural implementation compares the TOC against the same in-memory heading list the TOC was built from. That comparison cannot fail. It proves the program is self-consistent and proves nothing about the document. The only comparison with content is TOC versus the delivered document's own XML.

## THREAT MODEL

A circular check: the script's heading list validating the script's TOC. A heading that exists in the body but never reaches the TOC. A TOC entry pointing at a heading that was renamed or removed. A hidden heading counted by one side and not the other.

## STATIC ANALYSIS

No module under `PROJECT_ROOT` may be imported. A top-level import executes code. Parse; do not import.

1. Resolve the target from L1-A03. If A03 returned BLOCKED_TARGET_IDENTITY_UNCERTAIN, this audit runs against a named candidate and says so in every conclusion.
2. PYTHON_AST_PARSE the exporter. Identify how the TOC is built and from what data structure.
3. Determine whether the TOC is a static list of paragraphs or an OOXML TOC field. This changes the comparison entirely: a field is resolved by Word, not by the generator.
4. Identify the heading style names the generator uses, and whether it recognises any other heading styles.
5. Record whether any existing self-check compares TOC against the generator's own list — and if so, name it as the circular check.

## RUNTIME TEST MATRIX

Every runtime operation below is gated and requires the human approval token. Nothing here runs before that token arrives.

1. Generate a document from a synthetic fixture inside the audit work directory, via PYTHON_SCRIPT_RUN_SANDBOX.
2. Extract the real heading set from the generated document independently: unzip word/document.xml in the sandbox, parse with defusing options, select paragraphs by style, and record text, order and nesting level.
3. Extract the TOC entries independently from the generated document, not from the generator's memory.
4. Compare: text equality, order, hierarchy level, and anchor/bookmark mapping where the format carries one.
5. Fixture matrix, each a separate generation: T1 baseline; T2 a heading removed from the source after the TOC list is built; T3 a duplicate heading with identical text; T4 a renamed heading; T5 a hidden heading (vanish property set); T6 a heading present in body but excluded from the TOC; T7 a TOC entry with no matching body heading.

## POSITIVE CONTROL

T1 baseline must show complete agreement. If the baseline disagrees, the extractor is wrong and must be fixed before anything else is interpreted.

## NEGATIVE CONTROL

A document with zero headings must yield an empty TOC and an empty heading set, agreeing trivially. This proves the comparison does not manufacture entries.

## MUTATION CONTROL

T2, T4 and T6 are the mutation controls. Each must be detected by the comparison. If a removed heading, a renamed heading and a body-only heading all compare equal, the comparison is not comparing.

## INDEPENDENT ORACLE

An independent OOXML reader written for this audit. Under no circumstances may the exporter's internal heading list serve as the reference side of the comparison.

Forbidden as an oracle for this audit: the implementation under test, any other copy of it, any project artefact derived from it, any prior report under `docs/`, this package's own reconciliation notes, any output of the failed predecessor package, and model knowledge unsupported by a retrieved source.

## EDGE CASES

- heading text differing only by a non-breaking space
- heading text differing only by case
- two headings with identical text at different levels
- a heading inside a table cell
- a heading inside a text box or header/footer
- a TOC that is a field code and has never been updated

## PASS CRITERIA

Baseline agrees; every mutation fixture is detected; and the comparison is demonstrably against the generated document's own XML rather than the generator's heading list.

In addition, and without exception: positive control passed, negative control passed, mutation control passed where applicable, independent oracle used, target hash unchanged across the run, and no unresolved evidence capable of changing the conclusion. If such evidence exists the verdict is `UNVERIFIED`, not `PASS`.

## PASS_WITH_WARNINGS CRITERIA

Agreement holds for body headings but headings in headers, footers or text boxes are outside the comparison, and that boundary is named.

Every warning is named with its own evidence. A warning is not a place to put doubt about the main conclusion — that belongs in `UNVERIFIED`.

## FAIL CRITERIA

A mutation fixture compares equal; or the only comparison available is the circular one.

## BLOCKED CRITERIA

L1-A03 could not identify a target and no candidate can be justified even provisionally; or the TOC is a Word-resolved field that cannot be evaluated without opening Word, which is forbidden.

A blocked audit is a legitimate and complete outcome. State precisely what is missing and what would unblock it. Never soften BLOCKED into PASS or into a partial pass.

## UNVERIFIED CRITERIA

The TOC is a field code, its resolution is deferred to the word processor, and no offline resolution is possible. Say that; do not approximate it.
