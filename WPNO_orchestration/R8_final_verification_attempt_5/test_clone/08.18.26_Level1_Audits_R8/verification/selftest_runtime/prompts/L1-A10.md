## OBJECTIVE

Locate every copy of the reference checker, hash each, identify the repository and git HEAD, identify the productive caller and the host or container in which it runs, distinguish backup, golden and test copies, and prove the productive copy from execution evidence.

A checker that produces the citation verdicts on which a filing depends must be identified exactly, or every verdict it produced is attributable to an unknown file.

## TARGET IDENTIFICATION RULE

Re-derive the target set yourself; do not adopt the binding's list as the enumeration. Then compare your enumeration against the binding. A file present in one and not the other is a finding before anything else proceeds.

Hash every candidate with `SHA256_FILE` and compare against the binding. Any mismatch means the tree changed since the package was built: stop and return `BUILD_CONTAMINATED_SOURCE_CHANGED`.

Production identity requires execution-path evidence — an import, an invocation in a script, a container command, a workflow node, a scheduler entry. Filename, version suffix, modification time, file size, documentation, comments and proximity to another file are **excluded by rule**. If production identity cannot be proven, say so; do not nominate a most-likely candidate.

## PRODUCTION PATH REQUIREMENT

State, as a separate recorded item, whether the target is on the production execution path, and on what evidence.

This machine has no runtime supervisor for most audited components: the only two WPNO LaunchAgents are an MCP health poller and a wiki ingest watcher whose watch path is outside `PROJECT_ROOT`, and the only container mounting WPNO source mounts four named files under `docker/litellm`. Everything else in scope is invoked by hand from a shell. Consequently 'productive' is frequently unprovable here, and `BLOCKED_TARGET_IDENTITY_UNCERTAIN` or `UNVERIFIED` is the correct answer rather than a qualified guess.

If the audit proceeds against a candidate rather than a proven productive copy, every conclusion must carry that qualification in its own text — not only in a footnote.

## THREAT MODEL

An old copy in the execution path while a corrected copy sits in the working tree. A copy inside a container that diverged from the host. A test copy mistaken for the productive one because it is newer.

## STATIC ANALYSIS

No module under `PROJECT_ROOT` may be imported. A top-level import executes code. Parse; do not import.

1. Search PROJECT_ROOT and the Discovery hash inventory for every file whose name or content identifies it as this checker.
2. SHA256_FILE each and compare against this audit's binding.
3. GIT_STATUS_READONLY, GIT_REV_PARSE and GIT_LOG_READONLY: record the repository, HEAD, and whether each copy is tracked, ignored or untracked.
4. Search for callers across source, shell scripts, compose files, Dockerfiles, workflow JSON, MCP configuration and LaunchAgent definitions.
5. Determine host versus container status per copy: is it bind-mounted, copied by a Dockerfile, or neither.
6. Classify each copy: productive candidate, backup, golden, test, historical.
7. Record the reference data file separately — bgh_referenz.json is data the checker loads, and a divergence there changes verdicts without changing the code.

## BLOCKED CRITERIA
