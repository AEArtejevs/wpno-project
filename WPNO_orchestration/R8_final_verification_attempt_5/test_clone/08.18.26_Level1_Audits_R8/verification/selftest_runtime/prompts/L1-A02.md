## TITLE

verify_document semantic verification versus existence-only check

## RISK

```text
HIGH
```

## OBJECTIVE

Determine what verify_document actually asserts about a document, and whether a document that parses but is semantically wrong passes it.

## WHY THIS MATTERS

A verifier that only proves a file exists and opens is a verifier in name. It returns success for a truncated document, a document with the body replaced, and a document whose table of contents no longer matches its headings. Downstream, that success is read as 'the document was verified'. The gap between those two statements is where a wrong document gets filed.

## THREAT MODEL

Existence-only or parse-only verification returning success. Exception-swallowing that converts a structural failure into a pass. A check that validates the file it just wrote rather than the file that will be delivered.

## STATIC ANALYSIS

No module under `PROJECT_ROOT` may be imported. A top-level import executes code. Parse; do not import.

1. PYTHON_AST_PARSE the target. Do not import it.
2. Enumerate every assertion the module makes: what is compared, against what, and what causes a non-success return.
3. Identify every try/except and record what each swallows. An except that returns success is the defect this audit exists to find.
4. Identify the return contract: exit code, boolean, exception, printed text. Record whether a caller could mistake one for another.
5. Determine whether the check reads the document's XML parts or only opens the container.
6. List which of these are checked at all: body text, heading text, heading order, heading hierarchy, table of contents, relationships, content types, document properties, part integrity.

## RUNTIME TEST MATRIX

Every runtime operation below is gated and requires the human approval token. Nothing here runs before that token arrives.

1. Build the fixture matrix inside the audit work directory. All fixtures synthetic. Never a client document.
2. F1 valid document — expect success.
3. F2 missing file — expect a clear, distinguishable failure, not a crash indistinguishable from a rule failure.
4. F3 empty file (0 bytes) — expect failure.
5. F4 parseable but semantically wrong: valid OOXML, correct structure, body text replaced with unrelated content.
6. F5 modified body: one sentence changed.
7. F6 modified heading: one heading renamed.
8. F7 damaged TOC: TOC field retained, entries no longer matching headings.
9. F8 broken relationship: an r:id referenced from document.xml with no matching entry in the .rels part.
10. F9 truncated document: the ZIP cut at 60 percent of its length.
11. For each fixture: record argv, exit code, stdout, stderr, and the module's own verdict. Distinguish 'reported failure' from 'crashed'.
12. Build the result matrix: fixture x (expected, actual, distinguishable-from-success).

## POSITIVE CONTROL

F1 must pass. If a known-good document does not pass, the verifier is unusable and the rest of the matrix is uninterpretable.

## NEGATIVE CONTROL

F3 (empty file) must fail. A verifier that passes a zero-byte file has no content check at all.

## MUTATION CONTROL

F5, F6 and F9 are the mutation controls. At least one must cause a failure. If a modified body, a renamed heading and a truncated container all pass, the verifier does not verify the document — it verifies that a file is there, and the audit says exactly that.

## INDEPENDENT ORACLE

An independent reader written for this audit using zipfile and xml.etree with external entities and DTD disabled, which extracts the heading list and body text directly from word/document.xml. The oracle states what the document contains; the target states what it claims. They are compared. verify_document is never its own oracle.

Forbidden as an oracle for this audit: the implementation under test, any other copy of it, any project artefact derived from it, any prior report under `docs/`, this package's own reconciliation notes, any output of the failed predecessor package, and model knowledge unsupported by a retrieved source.

## EDGE CASES

- file with a .docx name that is not a ZIP
- valid ZIP that is not OOXML
- document with zero headings
- document with duplicate identical headings
- document whose TOC field is present but never updated
- file readable but with no read permission on a part

## PASS CRITERIA

F1 passes; F2, F3, F9 fail distinguishably; at least one of F5/F6/F7/F8 fails; the module's assertions enumerated statically match its observed behaviour; and no exception handler converts a structural failure into success.

In addition, and without exception: positive control passed, negative control passed, mutation control passed where applicable, independent oracle used, target hash unchanged across the run, and no unresolved evidence capable of changing the conclusion. If such evidence exists the verdict is `UNVERIFIED`, not `PASS`.

## PASS_WITH_WARNINGS CRITERIA

The verifier catches structural damage but not semantic substitution (F4 passes), and this is stated as a named limitation with the exact class of substitution it misses.

Every warning is named with its own evidence. A warning is not a place to put doubt about the main conclusion — that belongs in `UNVERIFIED`.

## FAIL CRITERIA

File existence or parser success alone yields a pass — that is, F3, F5, F6 and F9 all pass. Or an exception handler is shown to convert failure into success.

## BLOCKED CRITERIA

A blocked audit is a legitimate and complete outcome. State precisely what is missing and what would unblock it. Never soften BLOCKED into PASS or into a partial pass.
