## OBJECTIVE

Determine which payload scanner copy is actually inside the productive image or container, with image ID, digest, creation timestamps, mounts, entrypoint, command, build-context evidence and container mapping — and determine whether the image was rebuilt after the relevant 04.08 change.

## WHY THIS MATTERS

A scanner corrected on the host protects nothing if the container runs a copy baked into an image built before the correction. This is the containerised form of the duplicate-copy failure the project has already suffered, and it is harder to see because the divergent copy is not visible in the filesystem.

## TARGET IDENTIFICATION RULE

Re-derive the target set yourself; do not adopt the binding's list as the enumeration. Then compare your enumeration against the binding. A file present in one and not the other is a finding before anything else proceeds.

Hash every candidate with `SHA256_FILE` and compare against the binding. Any mismatch means the tree changed since the package was built: stop and return `BUILD_CONTAMINATED_SOURCE_CHANGED`.

Production identity requires execution-path evidence — an import, an invocation in a script, a container command, a workflow node, a scheduler entry. Filename, version suffix, modification time, file size, documentation, comments and proximity to another file are **excluded by rule**. If production identity cannot be proven, say so; do not nominate a most-likely candidate.

## PRODUCTION PATH REQUIREMENT

State, as a separate recorded item, whether the target is on the production execution path, and on what evidence.

This machine has no runtime supervisor for most audited components: the only two WPNO LaunchAgents are an MCP health poller and a wiki ingest watcher whose watch path is outside `PROJECT_ROOT`, and the only container mounting WPNO source mounts four named files under `docker/litellm`. Everything else in scope is invoked by hand from a shell. Consequently 'productive' is frequently unprovable here, and `BLOCKED_TARGET_IDENTITY_UNCERTAIN` or `UNVERIFIED` is the correct answer rather than a qualified guess.

If the audit proceeds against a candidate rather than a proven productive copy, every conclusion must carry that qualification in its own text — not only in a footnote.

## THREAT MODEL

Assuming a bind mount where the Dockerfile copies, or the reverse. Reading the compose file as a description of what is running rather than of what would run if started. Concluding from an image build date that a file inside it is current, when the file may be mounted over.

## STATIC ANALYSIS

No module under `PROJECT_ROOT` may be imported. A top-level import executes code. Parse; do not import.

1. Read docker-compose.yml. Enumerate every volume entry and classify each as bind mount or named volume.
2. Record the finding that payload_scan.py is bind-mounted: ./payload_scan.py:/app/payload_scan.py. For a bind mount, the in-container content is the host content while the container runs, so the rebuild question does not apply to this file — but it does apply to anything the Dockerfile COPYs. Establish both, and do not answer one while claiming the other.
3. Read the Dockerfile. Enumerate every COPY and ADD and record what is baked in.
4. Read the compose entrypoint and command, and the Dockerfile's ENTRYPOINT and CMD, and record which would win.
5. Read custom_callback.py and record how it imports and invokes payload_scan, including any sys.path manipulation.
6. Record the host file's hash and mtime for every bind-mounted path.

## RUNTIME TEST MATRIX

Every runtime operation below is gated and requires the human approval token. Nothing here runs before that token arrives.

1. Do NOT access the Docker socket. Do NOT run docker, docker compose, docker inspect, or any container command.
2. Locate the operator-produced Docker metadata export in references/ (REF-13). Verify its hash against references/manifest.json.
3. From the export, extract: image ID, image digest, image creation timestamp, container creation timestamp, container state, mounts as actually attached, effective entrypoint and command, and build-context evidence.
4. Compare the attached mounts against the compose declaration. A difference between declared and attached is a finding.
5. Compare the image creation timestamp against 2026-08-04, the date of the change in question, and state whether the image predates it.
6. For any file baked into the image, compare its hash against the host copy. That hash may only come from an operator-produced export.
7. If no export is supplied: UNVERIFIED_DOCKER_PRODUCTIVE_COPY. Say exactly which questions remain open.

## EDGE CASES

- a container started from an older image than the current tag
- a mount attached at runtime that the compose file does not declare
- an image with the same tag and a different digest
- a stopped container whose state still matters for what ran on 04.08
- a build cache layer masking a change

## PASS CRITERIA

The productive copy is proven, its hash matches a known host copy, mounts as attached match the declaration, and the rebuild question is answered for every baked-in file.

In addition, and without exception: positive control passed, negative control passed, mutation control passed where applicable, independent oracle used, target hash unchanged across the run, and no unresolved evidence capable of changing the conclusion. If such evidence exists the verdict is `UNVERIFIED`, not `PASS`.

## PASS_WITH_WARNINGS CRITERIA
