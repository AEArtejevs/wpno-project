## TITLE

## RISK

```text
HIGH
```

## OBJECTIVE

Establish whether two runs of the productive assembly path, given identical input and identical configuration, produce byte-identical output; and where they do not, establish exactly which bytes differ and whether those bytes are document content or container metadata.

## WHY THIS MATTERS

A document assembler that is not deterministic cannot be audited, cannot be reproduced by an opponent, and cannot support a claim that a filed document is the document that was reviewed. If the output differs run to run, every downstream hash-based control in this system is measuring noise. The distinction between a timestamp inside a ZIP header and a changed sentence in the body is the whole point: one is harmless, the other is a different document, and a naive diff calls both 'changed'.

## THREAT MODEL

A nondeterministic assembler hides content drift inside expected metadata churn. An auditor who normalizes before hashing sees stability that does not exist. An auditor who only compares raw hashes sees instability that is meaningless. Either error makes the control useless in opposite directions.

## STATIC ANALYSIS

No module under `PROJECT_ROOT` may be imported. A top-level import executes code. Parse; do not import.

1. Parse the target with PYTHON_AST_PARSE. Do not import it.
2. Enumerate every source of nondeterminism reachable from module scope and from the assembly entry point: datetime/time calls, uuid, random, os.urandom, hash-order-dependent iteration over dict or set, os.listdir/glob ordering, locale-dependent formatting, tempfile names, environment reads.
3. Enumerate every write target and every path the module constructs.
4. Identify the entry point and its full argument surface (argv, environment, config file).
5. Determine the output container format. If it is a ZIP-based format (DOCX), record that ZIP local headers carry mtime, and that this alone will break byte equality unless the writer pins it.
6. Identify any caller. Record that no caller was found in-tree if that is the result — do not leave the question unanswered.

## RUNTIME TEST MATRIX

Every runtime operation below is gated and requires the human approval token. Nothing here runs before that token arrives.

1. Prepare two clean, separate work directories under the audit work directory: RUN1 and RUN2. Neither may pre-exist.
2. Copy the input fixture into each. The fixture is synthetic and is built inside the audit work directory. Never a client document.
3. Pin the environment identically for both runs: TZ, LC_ALL, LANG, PYTHONHASHSEED, SOURCE_DATE_EPOCH if the code honours it. Record the exact environment allowlist used.
4. Run the assembler once per directory, via PYTHON_SCRIPT_RUN_SANDBOX, with a fixed timeout and output limit. Record argv, exit code, stdout, stderr for each.
5. SHA256_FILE the raw output of each run before touching it in any way.
6. COMPARE_HASHES. If equal, record and proceed to the controls.
7. If unequal, COMPARE_BINARY_FILES and locate the differing byte ranges.
8. For a ZIP container: ZIP_LIST both, compare the entry lists, entry order, sizes, CRCs and stored timestamps. Then, and only then, extract into the sandbox and compare entry payloads individually.
9. Classify every difference as: container timestamp, container ordering, document property (creator, revision, created/modified), or document content.
10. Only after the raw comparison is complete and recorded, perform a normalized comparison as an ADDITIONAL result.

## POSITIVE CONTROL

Introduce a known one-character difference into the RUN2 input fixture in the sandbox. The raw hashes must differ, and the located difference must be the one introduced. This proves the comparison can see a change.

## NEGATIVE CONTROL

Run the assembler twice on the same input in the same directory-shape without any change. Any difference observed here is nondeterminism, not input variation. This separates the two causes.

## MUTATION CONTROL

Pin all identified nondeterminism sources (fixed TZ, fixed PYTHONHASHSEED, fixed SOURCE_DATE_EPOCH) and repeat. If the output becomes deterministic, the nondeterminism is environmental. If it does not, it is in the code, and the AST enumeration must be re-examined for what it missed.

## INDEPENDENT ORACLE

The independent oracle is the ZIP/OOXML structure itself, read with the standard library's zipfile and a byte-level comparison written for this audit. The assembler must never be used to explain its own output. A prior report in docs/ is not an oracle.

Forbidden as an oracle for this audit: the implementation under test, any other copy of it, any project artefact derived from it, any prior report under `docs/`, this package's own reconciliation notes, any output of the failed predecessor package, and model knowledge unsupported by a retrieved source.

## EDGE CASES

- empty input
- input with a single heading and no body
- input containing non-ASCII and combining characters
- input large enough to change ZIP compression choices
- two runs separated by a clock change across a second boundary
- two runs under different working-directory depths

## PASS CRITERIA

Two runs on identical input under an identically pinned environment produce byte-identical raw output; the positive control detects an injected change; the negative control shows no difference; and every difference class the static analysis predicted was either absent or accounted for.

In addition, and without exception: positive control passed, negative control passed, mutation control passed where applicable, independent oracle used, target hash unchanged across the run, and no unresolved evidence capable of changing the conclusion. If such evidence exists the verdict is `UNVERIFIED`, not `PASS`.

## PASS_WITH_WARNINGS CRITERIA

Raw output differs only in container metadata that is fully enumerated and shown not to affect document content, and the normalized comparison is identical. The warning names each metadata field.

Every warning is named with its own evidence. A warning is not a place to put doubt about the main conclusion — that belongs in `UNVERIFIED`.

## FAIL CRITERIA

Document content differs between two runs on identical input; or a difference cannot be classified; or the positive control fails to detect the injected change.

## BLOCKED CRITERIA

The entry point cannot be invoked without an unavailable dependency or an operator-supplied input; or human approval for PYTHON_SCRIPT_RUN_SANDBOX is not given.

A blocked audit is a legitimate and complete outcome. State precisely what is missing and what would unblock it. Never soften BLOCKED into PASS or into a partial pass.

## UNVERIFIED CRITERIA

Runs completed but a difference remains unclassified after the extraction-level comparison, and no further evidence is available offline.
