Output guard permits the known-good report

## RISK


## OBJECTIVE

Prove that the productive guard accepts the known-good report, that the acceptance is a real evaluation rather than a skipped or no-op execution, and that no suppression mechanism is hiding a rejection.

## WHY THIS MATTERS

The false-positive side of a guard decides whether people keep using it. A guard that rejects correct work is disabled within a week, and then protects nothing. Equally, an acceptance that came from a guard that never ran is worse than a rejection: it is a recorded success with no evaluation behind it.

## THREAT MODEL

A no-op run counted as acceptance: an early return, an unmet precondition, an empty rule set, a silently caught exception, a configuration file that was not found. Any of these produce 'no findings' and exit 0.

## STATIC ANALYSIS

No module under `PROJECT_ROOT` may be imported. A top-level import executes code. Parse; do not import.

1. Resolve the known-good input identity from evidence. 'report_good' does not exist as an identifier in PROJECT_ROOT; it appears once in a GODAUDIT log. Establish the mapping or return BLOCKED_TARGET_IDENTITY_UNCERTAIN.
2. Resolve the productive guard version, as in L1-A05.
3. PYTHON_AST_PARSE the guard and enumerate every early-return path, every exception handler, every precondition, and every configuration or data file it loads.
4. Identify what the guard does when a required configuration or pattern file is missing: block, or pass silently. A guard that passes when its rules failed to load is the defect.
5. Determine how many rules are expected to be evaluated for a given input, so that 'rules evaluated' can be counted at runtime.

## RUNTIME TEST MATRIX

Every runtime operation below is gated and requires the human approval token. Nothing here runs before that token arrives.

1. Run the productive guard against the known-good input. Record argv, exit code, complete stdout and stderr.
2. Count rules actually evaluated. If the guard does not report this, instrument a sandbox copy to count, and state that the count comes from an instrumented copy whose hash is recorded.
3. Zero rules evaluated with exit 0 is NOT a pass. It is the vacuous-success pattern this project has already suffered (CLAUDE.md § 10, bullet 4) and it is a FAIL for this audit.
4. Remove the guard's configuration/pattern file in the sandbox copy's environment and re-run: record whether the guard blocks or passes silently.
5. Re-run the known-good input with each rule individually neutralised in the sandbox copy to confirm the rule set is live.

## POSITIVE CONTROL

The known-bad input from L1-A05 must be rejected by this same invocation path. This proves the guard was actually evaluating during this audit's runs, and is the single most important control here.

## NEGATIVE CONTROL

The known-good input must be accepted. That is the audit's claim, and on its own it is worth nothing without the positive control above.

## MUTATION CONTROL

Insert one known-bad token into a copy of the known-good input. It must now be rejected. If a known-good document remains accepted after a known-bad token is added, acceptance is not an evaluation.

## INDEPENDENT ORACLE

The rule enumeration from the AST parse, plus the rule-evaluation count. Acceptance is only meaningful relative to the number of rules that ran.

Forbidden as an oracle for this audit: the implementation under test, any other copy of it, any project artefact derived from it, any prior report under `docs/`, this package's own reconciliation notes, any output of the failed predecessor package, and model knowledge unsupported by a retrieved source.

## PASS CRITERIA

The known-good input is accepted; the rule-evaluation count is greater than zero and matches the static expectation; the positive control (known-bad rejected) holds on the same path; the mutation control converts acceptance into rejection; and the missing-configuration case blocks rather than passing silently.

In addition, and without exception: positive control passed, negative control passed, mutation control passed where applicable, independent oracle used, target hash unchanged across the run, and no unresolved evidence capable of changing the conclusion. If such evidence exists the verdict is `UNVERIFIED`, not `PASS`.

## PASS_WITH_WARNINGS CRITERIA

Acceptance is real and rules ran, but the guard passes silently when its configuration file is absent. Name this as a warning with the exact file.

Every warning is named with its own evidence. A warning is not a place to put doubt about the main conclusion — that belongs in `UNVERIFIED`.

## FAIL CRITERIA

Acceptance with zero rules evaluated; or the mutation control is still accepted; or the known-bad input is also accepted on this path.

## BLOCKED CRITERIA

The known-good input cannot be identified from evidence.

A blocked audit is a legitimate and complete outcome. State precisely what is missing and what would unblock it. Never soften BLOCKED into PASS or into a partial pass.

## UNVERIFIED CRITERIA

Rules evaluated could not be counted and no instrumented copy could be made.
