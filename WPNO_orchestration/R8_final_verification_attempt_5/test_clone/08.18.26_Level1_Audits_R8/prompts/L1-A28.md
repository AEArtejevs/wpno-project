## TITLE

Independent messageDigest remeasurement

## RISK

```text
HIGH
```

## OBJECTIVE

Identify the exact signed content, determine whether it is encapsulated or detached, identify the digest algorithm, extract the messageDigest signed attribute without treating the parse as verification, recalculate the digest independently, and compare exact bytes.

## WHY THIS MATTERS

Three different things are routinely conflated: the digest of the content, the digest recorded in the signed attributes, and the cryptographic verification of the signature over those attributes. Each can succeed while another fails. Reporting one as the other is the most common error in signature forensics, and it produces a confident conclusion that is exactly backwards.

## THREAT MODEL

Reporting a successful parse as a successful verification. Recalculating the digest over the wrong byte range — the encapsulated content versus the file versus the canonicalised form. Comparing a hex string against a base64 string and concluding they differ.

## STATIC ANALYSIS

No module under `PROJECT_ROOT` may be imported. A top-level import executes code. Parse; do not import.

1. Locate the CMS object and its content in references/ (REF-11). If absent: BLOCKED.
2. Determine encapsulated versus detached: does the CMS structure carry the content, or does it reference external content? This determines what is hashed and everything downstream depends on it.
3. Parse the CMS structure with OPENSSL_PARSE_CERT / an ASN.1 read. Record the structure. Mark the result PARSE_ONLY_NOT_VERIFICATION.
4. Identify the digest algorithm from the structure, not from an assumption.
5. Extract the messageDigest signed attribute as raw bytes and record it in hex.

## RUNTIME TEST MATRIX

Every runtime operation below is gated and requires the human approval token. Nothing here runs before that token arrives.

1. Determine the exact byte range the digest is supposed to cover, and state it explicitly before computing anything.
2. Recalculate the digest over that range independently, using a method that does not use the CMS library that parsed the structure.
3. Compare the recalculated digest against the extracted attribute byte for byte, in a single representation. Convert both to lowercase hex before comparing, and record both original representations.
4. Report three results separately and never merge them: (a) the content digest as recalculated; (b) the messageDigest signed attribute as extracted; (c) whether they match. Note explicitly that (c) matching does NOT establish that the signature verifies — that is L1-A34.
5. Record the exact commands and exit codes.

## POSITIVE CONTROL

Compute the digest of a known input whose digest is independently known and confirm the method is correct.

## NEGATIVE CONTROL

Compute the digest of a different input and confirm it differs.

## MUTATION CONTROL

Alter one byte of a sandbox copy of the content and recalculate. The digest must change and must no longer match the attribute. This proves the comparison is sensitive.

## INDEPENDENT ORACLE

An independent hash computation over an explicitly stated byte range, plus the ASN.1 structure read directly. The signing tool's own verification output is not the oracle for this question.

Forbidden as an oracle for this audit: the implementation under test, any other copy of it, any project artefact derived from it, any prior report under `docs/`, this package's own reconciliation notes, any output of the failed predecessor package, and model knowledge unsupported by a retrieved source.

## EDGE CASES

- detached content whose file has a trailing newline the signer did not include
- content that was canonicalised before signing
- multiple signers with different messageDigest values
- a digest algorithm that differs between the signed attributes and the signature algorithm
- an attribute encoded with a non-minimal length

## REGRESSION REQUIREMENTS

The byte range, the algorithm, both digests in hex, and the match result.

## PASS CRITERIA

Content and range are identified; the algorithm is read from the structure; the digest is independently recalculated and compared byte for byte; and the three results are reported separately with the parse marked as not-verification.

In addition, and without exception: positive control passed, negative control passed, mutation control passed where applicable, independent oracle used, target hash unchanged across the run, and no unresolved evidence capable of changing the conclusion. If such evidence exists the verdict is `UNVERIFIED`, not `PASS`.

## PASS_WITH_WARNINGS CRITERIA

Every warning is named with its own evidence. A warning is not a place to put doubt about the main conclusion — that belongs in `UNVERIFIED`.

## FAIL CRITERIA

## BLOCKED CRITERIA

## UNVERIFIED CRITERIA
