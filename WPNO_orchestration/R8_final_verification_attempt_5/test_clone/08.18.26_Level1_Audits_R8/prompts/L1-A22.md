## OBJECTIVE

Determine whether the golden test is collected, and if it is not, determine the cause from the full list of possible causes; then determine, in a sandbox copy, what the test would report if it were collected.

## WHY THIS MATTERS

A golden test exists to catch divergence between a reference implementation and a live one. A golden test that is never collected reports nothing, and its silence is filed as a pass. This is the project's own error class 8: pytest reported five passed while nothing exercised the new code. The number of green tests says nothing about which tests ran.

## THREAT MODEL

A test that never runs, in a suite whose exit code is 0. A collection error swallowed by the runner's summary. A test collected but skipped by a marker or a missing fixture. A test whose import fails silently because a path is missing from pythonpath.

## STATIC ANALYSIS

No module under `PROJECT_ROOT` may be imported. A top-level import executes code. Parse; do not import.

1. Read pytest.ini and record verbatim: addopts, testpaths, norecursedirs, pythonpath.
2. Check each of the thirteen candidate causes explicitly and record a finding for each: file naming; function naming; class naming; pytest configuration; test discovery patterns; package boundaries; import errors; syntax errors; skip markers; xfail; fixtures; test root; invocation path.
3. Note without assuming: anonymization/golden is under a testpaths entry, the filename ends in _test.py which matches a default pattern, pythonpath includes anonymization but not anonymization/golden, and norecursedirs does not exclude golden. Verify each of these against the file rather than taking them from this prompt.
4. AST-parse the golden test and record what it imports, how it locates the copies it compares, and what it asserts.
5. Determine whether an __init__.py exists in anonymization/golden, and what that implies under --import-mode=importlib.

## RUNTIME TEST MATRIX

Every runtime operation below is gated and requires the human approval token. Nothing here runs before that token arrives.

1. Create a sandbox copy of the tree under the audit work directory. All pytest work happens there. Never in PROJECT_ROOT — a collection run creates __pycache__ and .pytest_cache, which would be a write into a read-only root.
2. PYTEST_COLLECT_SANDBOX from the project root of the sandbox copy, exactly as the project would be invoked. Record the complete collection output including errors and the collected count.
3. PYTEST_COLLECT_SANDBOX again, this time targeting the golden test file directly by path. Compare. A file collectable by path but not by the default invocation is a configuration finding, not a file finding.
4. If collection fails, apply one candidate cause at a time in the sandbox and record which single change makes it collect. Change one thing at a time or the cause cannot be attributed.
5. Once it collects, PYTEST_RUN_SANDBOX and record what it reports: pass, fail, skip, error — and the assertion detail.
6. Never rename or modify the real test.

## POSITIVE CONTROL

A trivially collectable test placed in the same sandbox directory must be collected. This proves the collection run works and isolates the cause to the file or its configuration.

## NEGATIVE CONTROL

A file deliberately named so as not to match any pattern must not be collected. This proves collection is selective.

## MUTATION CONTROL

Once the test collects and passes in the sandbox, alter the golden copy so it diverges from the live copy. The test must fail. A golden test that passes when the copies differ is not a golden test.

## INDEPENDENT ORACLE

The pytest configuration read directly, plus the collection report itself. The suite's exit code is the thing under test.

Forbidden as an oracle for this audit: the implementation under test, any other copy of it, any project artefact derived from it, any prior report under `docs/`, this package's own reconciliation notes, any output of the failed predecessor package, and model knowledge unsupported by a retrieved source.

## EDGE CASES

- a test collected under one interpreter and not another — `docker/litellm/__pycache__` holds both a `cpython-311` and a `cpython-314` artefact for `test_payload_scan`; verify this on the live tree rather than inheriting it
- a conftest.py altering collection
- an import error reported as a warning rather than an error
- a fixture that returns empty and makes every assertion vacuous
- a package boundary created by a stray __init__.py
