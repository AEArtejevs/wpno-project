## OBJECTIVE

Determine whether CLAUDE.md is tracked, ignored, untracked, outside the repository, symlinked or generated — and determine whether it would survive git clean -fd, without ever running that command in the real repository.

## WHY THIS MATTERS

An instruction file that a routine cleanup deletes is one command away from vanishing, and its absence is silent: the next session simply proceeds without it. Determining survivability by running the destructive command is not an audit, it is the incident.

## THREAT MODEL

Running git clean -fd to find out. Inferring tracked status from the file's presence. Ignoring the case where the file is tracked but a local modification is uncommitted, so cleanup preserves the committed version and discards the working one.

## STATIC ANALYSIS

No module under `PROJECT_ROOT` may be imported. A top-level import executes code. Parse; do not import.

1. GIT_STATUS_READONLY: record the file's porcelain status.
2. Use git ls-files to determine tracked status. A file listed there is tracked.
3. Use git check-ignore semantics by reading .gitignore and every applicable nested ignore file, and record which rule, if any, matches.
4. STAT_FILE: determine whether the path is a regular file or a symlink. If a symlink, resolve the target and record whether the target is inside the repository.
5. Determine whether the file is generated by any script in the tree, by searching for writes to that path.
6. GIT_LOG_READONLY on the path: record whether it has commit history.
7. Establish, from git semantics rather than from experiment, what git clean -fd would do to a file in the observed state: tracked files are untouched; ignored files are untouched by -fd without -x; untracked and not-ignored files are removed.

## RUNTIME TEST MATRIX

Every runtime operation below is gated and requires the human approval token. Nothing here runs before that token arrives.

1. git clean -nd (dry run) may be used ONLY with explicit human approval, and only in the real repository if that approval is given. It writes nothing, but it is still an operation on the real repository and is treated as gated.
2. The survivability question is properly answered in a disposable environment: create a synthetic repository under the audit work directory, reproduce the observed state (tracked, or untracked, or ignored), and run git clean -fd there. Record the outcome.
3. The synthetic repository must contain no project content — only files reproducing the state under test.
4. Compare the synthetic result against the state-based prediction. Agreement is the result; disagreement means the state was misclassified.

## POSITIVE CONTROL

In the synthetic repository, an untracked file must be removed by git clean -fd. This proves the reproduction is faithful.

## NEGATIVE CONTROL

In the synthetic repository, a tracked file must not be removed. This proves the command is selective.

## MUTATION CONTROL

In the synthetic repository, move the file between states (tracked, untracked, ignored) and confirm the outcome changes accordingly. This proves the state classification determines the outcome.

## INDEPENDENT ORACLE

Git's documented semantics plus the disposable-repository experiment. The real repository is never the experiment.

Forbidden as an oracle for this audit: the implementation under test, any other copy of it, any project artefact derived from it, any prior report under `docs/`, this package's own reconciliation notes, any output of the failed predecessor package, and model knowledge unsupported by a retrieved source.

## EDGE CASES

- ignored by a nested .gitignore rather than the root one
- a symlink whose target is outside the repository
- the file present in the index but deleted from the working tree

## PASS CRITERIA

The state is determined from read-only git evidence; the predicted outcome is confirmed in a disposable repository; and git clean -fd was never run in the real repository.

In addition, and without exception: positive control passed, negative control passed, mutation control passed where applicable, independent oracle used, target hash unchanged across the run, and no unresolved evidence capable of changing the conclusion. If such evidence exists the verdict is `UNVERIFIED`, not `PASS`.

## PASS_WITH_WARNINGS CRITERIA

Every warning is named with its own evidence. A warning is not a place to put doubt about the main conclusion — that belongs in `UNVERIFIED`.

## FAIL CRITERIA

The file is untracked and not ignored, so a routine git clean -fd would delete the project's instruction file.

## BLOCKED CRITERIA
